# 검증 단계와 운영

결정 번호는 [00_DECISIONS.md](00_DECISIONS.md)를 따른다. 각 단계는 통과 조건을 **시작 전에** 기록하고, 결과를 본 뒤에 조건을 낮추지 않는다. 조건을 바꿔야 하면 이유와 날짜를 남기고 해당 단계를 처음부터 다시 한다.

## 1. 단계 개요

| 단계 | 환경 | AI | 통과하면 |
|---|---|---|---|
| V0 코드 검증 | 가상 거래소 | 가짜 응답 | V1 |
| V1 백테스트 | 과거 데이터 (SQLite) | 제외 | V2 |
| V2 데모 모의투자 | Bybit 데모 계정 + Oracle `RLG_DEMO` | 적용 | V3 |
| V3 실거래 | Bybit 실계정 + Oracle `RLG_LIVE` | 적용 | 운영 계속 |

## 2. V0 코드 검증

단위 테스트 외에 가상 거래소로 아래 상황을 재현하고, 기대 동작을 테스트로 고정한다.

| 상황 | 기대 동작 |
|---|---|
| 주문 전송 후 응답 없음 | `UNKNOWN` → orderLinkId로 조회 → 확정. 중복 주문 없음 |
| UNKNOWN 조회 결과가 부분 체결 | 체결 내역 반영 후 `PARTIALLY_FILLED`로 추적, 예약은 남은 수량 |
| UNKNOWN 주문을 계속 찾지 못함 (조회 지연·오류 포함) | 기한이 지나도 `UNKNOWN`·전체 수량 예약·신규 진입 중단 유지, 알림 |
| **조회 3종이 모두 성공·빈 결과, 포지션 일치가 여러 번 지속된 뒤 늦은 `OPEN` 도착** | 그 전까지 예약과 진입 정지가 계속 유지되어 있었음. `OPEN` 도착 후 정상 추적 |
| UNKNOWN 진입 주문에 orderLinkId 취소 성공 | 이어 오는 상태로 종결(일부 체결 반영), 남은 예약 해제 |
| UNKNOWN 진입 주문 취소에 "주문 없음" 오류 | `UNKNOWN` 유지, 예약·정지 유지 |
| 사용자 수동 `NOT_FOUND` 확정 뒤 그 주문의 체결 도착 (M3 이후) | 실제 상태로 고치고 체결 반영, 알림 |
| `CANCELLED`/`FILLED` 통지가 execution보다 먼저 도착 → 다른 계약 진입 검사 → 지연 execution | 검사 시점에 미반영 체결이 노출에 포함됨 (02 2.1절) |
| 미반영 체결이 시간 안에 안 들어옴 | 체결 내역 조회로 반영, 그동안 해당 계약 신규 진입 중단 |
| 같은 체결이 WS와 REST로 두 번 도착 | execId 중복 제거, 장부 한 번만 반영 |
| 취소 경합으로 `Filled` 두 번 도착 | 두 번째는 무시, 상태 `FILLED` 유지 |
| WS 체결이 REST 접수 응답보다 먼저 도착 | `CREATED/SUBMITTED`에서 바로 `FILLED`로 이동, 장부 정상 |
| `CANCELLED` 확정 뒤 같은 주문의 체결 도착 | 체결 반영, 상태는 `CANCELLED` 유지 |
| 부분 체결 후 취소 | 체결 수량만 장부 반영, 부착 손절 수량 = 체결 수량 |
| **진입 체결 직후, 후속 처리 전 강제 종료** | 거래소에 부착 손절이 이미 있음(가상 거래소도 Partial 손절을 체결과 동시에 생성). 재시작 후 장부가 손절과 함께 복구됨 |
| 전략 청산 시작 후 장시간(수 시간) 미복구 | 그동안 남은 수량은 원래 손절로 보호됨. 재시작 시 청산 의도대로 이어서 처리 (01 1.4절) |
| 청산 시장가(IOC)가 일부만 체결 / 거절 | 남은 수량은 손절로 보호된 채 재시도. 횟수 초과 시 해당 계약 신규 진입 중단·알림, 손절 유지 |
| 청산 확정 전 손절 취소 시도 | 일어나지 않음: 전략 보유 0이 체결 내역으로 확인된 뒤에만 손절 취소 |
| 청산과 손절이 동시에 체결되어 다른 전략까지 감소 | 초과분을 S2 → S1 순서로 장부에서 빼고, 손절 수량을 보유량에 맞추고, 알림 |
| 청산 완료 후 손절 정리 | 전략별 손절 수량 = 보유량, 계약별 합계 = 순포지션 |
| 숏 최초·추가 진입, 숏 축소, 롱 → 숏 전환 | 03 4.1절 부호 계약 표의 기대값 |
| 앱에서 직접 청산(외부 감소) | 신규 진입 중단, S2 → S1 순서로 장부 감소, 초과 손절 취소, 알림 |
| 개인 WS 끊김 중 체결 | 재연결 후 03 4.3절 동기화로 장부 복구, 그동안 신규 진입 없음 |
| REST 스냅샷 직후 손절 체결 | 버퍼링된 WS 이벤트 재생으로 반영, 안정화 확인 후에만 진입 허용 |
| 손절 수량이 보유량보다 부족 | 보호 재등록 → 실패 시 시장가 축소, 알림 |
| 프로세스 강제 종료 후 재시작 | [03_SYSTEM_ARCHITECTURE.md](03_SYSTEM_ARCHITECTURE.md) 4.3절 동기화로 복구, 정지 상태 유지 |
| Oracle 접속 끊김 | 신규 진입 중단, Watchdog 알림. **보호 작업(손절 재등록·추적 손절·청산)은 로컬 저널에 기록 후 성공**. DB 복구 후 저널 반영, 중복 없음 |
| Oracle 끊김 중 보호 주문 응답 불명 → 재시작 | 저널 반영 → orderLinkId로 UNKNOWN 해소, 중복 보호 주문 없음 |
| Oracle 끊김 중 같은 손절을 두 번 amend하고 한 번 cancel → 복구 | 저널의 작업 3건이 모두 `(operation_id, phase)` 단위로 반영되고 최종 상태가 거래소와 같음 (03 5.4절) |
| 저널에 `requested`만 쓰고 종료 | 재시작 시 작업 종류별로 거래소에서 결과 확인 후 반영 |
| 두 계약 동시 진입이 계좌 한도를 넘음 | 위험 게이트에서 하나만 통과 (02 2.1절) |
| 같은 봉 재전달 / AI 축소 후 다음 봉 | 주문 1건, 보충 주문 없음 (03 4.1절) |
| 시세 공백 / 지연 봉 | 신규 진입 중단, 공백 보충 후 재개 |
| AI 시간 초과 / 형식 오류 / 비용 상한 | 신규 진입 안 함, 손절·청산 정상 |
| 일일 한도·낙폭·연속 손실 도달 | 정해진 정지 상태와 해제 방식. HALTED `/resume`은 02 5.1절 예시대로 |
| 텔레그램 미등록 사용자 명령 | 무시하고 기록 |
| 부분 진입 → 손절로 보유 0 → 남은 진입 취소 응답 유실 또는 늦은 체결 → 새 신호 | 기존 진입 주문 종결 확정 전에는 새 에피소드 없음, 늦은 체결은 손절로 보호된 채 청산 (D64) |
| 저널 `requested` 부분 기록 실패 → 긴급 전송 성공 → 응답 유실 → 재시작 | 거래소 대조로 그 주문을 받아들임, 보호·청산 주문 중복 없음 (D65) |
| 거래일 경계 (UTC 00:00) | 기준 평가액 갱신, 일일 정지 자동 해제 |

## 3. V1 백테스트 (D32: 구간 이동 검증)

- 데이터 (D70): Bybit 공개 API의 BTCUSDT·ETHUSDT 일봉·1시간봉과 펀딩비 **최근 3년**. 1분봉은 손절·청산 사건이 겹친 구간 재검증(3.1절)에 필요한 구간만 받는다. 저장은 백테스트용 SQLite(D29).
- 방식: 예시로 12개월 구간에서 값을 정하고 다음 3개월에서 확인한다. 이를 3개월씩 옮기며 반복한다. **확인 구간 결과만** 성과로 집계한다. 구간마다 계좌를 새로 시작하고, **그 구간 안의 마지막 봉에서** 모두 청산한다(D78, 상세는 M2-04). 어떤 실행도 자기 구간 밖 가격을 쓰지 않는다.
- 반영 비용: 거래 수수료(지정가/시장가 구분), 슬리피지 가정, 펀딩비, 거래소 수량 단위 내림.
- 미래 정보 차단: 마감된 봉만 사용하고, S2는 그 시점의 S1 상태만 본다. 지표 계산 코드는 실거래와 같은 코드를 쓴다.
- 체결은 아래 **가상 체결 규칙**(3.1절)을 따른다.
- 결과 기록: 거래 수, 승률, 평균 손익비, 최대 낙폭, 월별 손익, 연속 손실 최대값, 전략별·계약별 분해. 이 값들이 V2의 "예상 범위" 기준이 된다.
- 통과 조건: 확인 구간 합계가 비용 차감 후 손실이 아니고, 최대 낙폭이 낙폭 한도(L6)보다 작다. 구체 수치는 3.2절(D88).
- 재설계 뒤 판정 이력: D96(BTC·ETH 2021-06 ~ 2023-09) INDETERMINATE → D97 새 종목 4개에서 S1-B 단독 주 판정 + S1-B × S2-P 부 판정(M2-06). 데모 진입은 주 판정 PASS로 정한다.

### 3.1 가상 체결 규칙 (D49)

M1 가상 거래소, M2 백테스트, V2 그림자 장부(4장)가 **같은 규칙**을 쓴다. 그래야 세 곳의 결과가 같은 의미를 갖는다.

| 항목 | 규칙 |
|---|---|
| 신호 시점 | 봉 마감 시각 t의 종가로 신호를 만든다 |
| 최초 체결 가능 시점 | 다음 봉(t부터 시작하는 봉)의 시가. 신호를 만든 종가로는 체결하지 않는다 |
| 시장가 | 다음 봉 시가 ± 슬리피지(불리한 방향). 수수료는 테이커 |
| 지정가 | 이후 봉의 가격이 지정가를 **넘어서야** 체결(닿기만 하면 미체결). 체결가는 지정가, 수수료는 메이커. 유효 기간(다음 봉 마감 전)이 지나면 취소 |
| 손절(시장가 조건부) | 봉의 저가(롱)/고가(숏)가 trigger에 닿으면 발동. 체결가는 trigger ± 슬리피지. 시가가 이미 trigger를 넘어 열리면(갭) 시가 ± 슬리피지 |
| 진입 봉 안의 손절 | 진입한 봉에서 손절 가격에 닿았으면 손절된 것으로 본다(보수적) |
| 한 봉에 여러 사건 | 손절과 다른 유리한 사건(청산 신호 가격 등)이 같은 봉에서 모두 가능하면 **손절이 먼저**라고 본다 |
| 더 짧은 데이터 | 위 보수적 가정이 결과를 크게 바꾸는지 확인하려면, 해당 구간을 1분봉으로 다시 돌려 비교한다(선택, 결과 보고서에 표시) |
| 펀딩비 (D87) | **저장된 펀딩 기록의 시각**에 포지션을 들고 있으면 그 기록의 펀딩비율로 정산한다. 펀딩 주기는 계약마다 다르고 바뀔 수 있어서(Bybit instruments-info `fundingInterval`) 시각을 고정하지 않는다 |
| 수량 | 거래소 수량 단위로 내림. 최소 수량 미만이면 주문하지 않음 |
| 경계 시각 처리 순서 (D76) | 시각 T(1시간 경계)에서: ① T에 끝나는 봉 동안의 체결·손절 처리 → ② T가 펀딩 시각이면 그 시점 보유 포지션에 펀딩 정산 → ③ T가 UTC 00:00이면 거래일 기준값 저장(펀딩 후 지갑 잔고, D72) → 일일 정지 해제 → **곧바로 위험 상태 재검사**(L5·L6, 넘어온 미실현 손실로 다시 정지될 수 있음) → ④ 마감 봉으로 신호 계산: S1(일봉) → S2(1시간봉), 계약은 BTCUSDT → ETHUSDT → ⑤ 주문 생성 → ⑥ 주문은 T부터 시작하는 봉의 시가부터 체결 가능 |
| 데이터 완전성 (D77) | 실행 전에 두 계약 모두 [구간 시작 − 워밍업, 구간 끝) 범위의 일봉·1시간봉이 빠짐없이 있고, 구간 안 펀딩 기록이 끊기지 않았는지 검사한다(D87: 이웃한 두 기록의 간격, 그리고 구간 시작·끝과 가장 가까운 기록 사이 간격이 수집 시점 펀딩 주기보다 길면 빠진 것). 하나라도 빠지면 그 구간은 **무효**로 실행하지 않고, 성과 집계와 V1 판정에서 뺀다(보고서에 표시). 빈 봉을 지어내거나 펀딩을 0으로 채우지 않는다 |
| 같은 시각 두 계약 | BTCUSDT → ETHUSDT 순서로 위험 게이트에 넣는다(결정적 순서) |

### 3.3 D98 재설계 2 검증 (초안, 2026-10-31, 확정 전 — PR #37 Codex 검토 반영)

BTC·ETH(2021~2026)와 D97 4종목(2022~2026)은 모두 관측된 데이터다. D98은 **기초 자산 단위로 데이터를 나눠** 아직 보지 않은 데이터를 확보한다. 진행은 두 단계다(D98): **1단계**(1~4)는 가볍게 우위를 확인하고, **2단계**(5)는 1단계를 통과했을 때만 운영 구조를 바꾸고 판정한다.

#### 1. 계약 범위와 데이터 수명 (1단계)

- **대상 계약**: `category=linear`, `contractType=LinearPerpetual`, `quoteCoin=USDT`, `settleCoin=USDT`, `status ∈ {Trading, Closed}`(PreLaunch·Delivering 제외). 공개 `instruments-info`를 페이지 끝까지 읽는다. 현재 메타데이터 목록이 과거 전체를 빠짐없이 담는지는 확인할 수 없으므로 한계로 적는다.
- **계약 수명**: 상장 = `launchTime`, 폐지 = `status=Closed`일 때 `deliveryTime`(무기한 폐지 시각, 0이면 폐지 시각 모름 → 그 계약은 제외하고 목록에 사유 기록). 계약 활성 구간 `[launch, delist)`.
- **정상 비활성과 누락의 구분**: 활성 구간 밖에는 데이터가 없는 것이 정상이다. 수집·검사는 활성 구간(워밍업 포함, 판정 범위로 자른 부분)에서만 연속성을 요구한다. 활성 구간 안의 1시간봉 공백은 누락이다.
- **폐지 처리(미래 정보 금지)**: 폐지 예정 시각을 미리 알고 진입을 피하지 않는다(진입 자격에 `deliveryTime`을 쓰지 않음). 폐지 시각에 열린 포지션은 **활성 구간 마지막 1시간봉 종가에서 불리한 방향으로 2% 미끄러진 가격**으로 청산한 것으로 본다(수수료 테이커, 그 사이 펀딩 없음). 마지막 봉과 폐지 시각 사이 공백은 누락으로 세지 않는다. 손실 종목을 조용히 빼지 않는다.
- **1단계 누락 처리**: 활성 구간 안 누락이 있는 계약은 누락 봉 앞뒤 30일 안의 신호를 연구에서 빼고, 뺀 신호 수·계약을 보고서에 적는다.
- **위험 등급(tier)·필터**: 1단계 신호 연구는 강제청산·노출 한도를 모델링하지 않으므로 쓰지 않는다. Closed 계약의 대체 모델 또는 INVALID_INPUT 처리는 2단계에서 정한다.
- **수집 계약 검증**: 판정용 풀 가격으로 가용성을 시험하지 않는다. 이미 관측한 Closed 계약(10000NFTUSDT·10000LADYSUSDT, 설계용 고정)과 합성 입력으로 검증한다.

#### 2. 기초 자산 키와 풀 분리 (1단계, 가격을 보기 전 한 번)

적용 순서는 고정이다: 필터(1) → 정규화 → 별칭 → 관측 예외 → 해시.
- **정규화**: `baseCoin`을 NFKC 정규화·대문자로 바꾼다. 앞이나 뒤에 붙은 10의 거듭제곱 배수(`10`~`10000000`, 예: `1000PEPE`, `SHIB1000`)를 떼되, 떼고 남은 이름이 비면 떼지 않는다. 숫자로 시작하는 실제 이름은 **예외 표**에 올려 떼지 않는다.
- **별칭 표**: 이름 변경으로 계약 이름이 바뀐 자산(예: MATIC→POL, RNDR→RENDER, FTM→S)을 한 키로 묶는다. 표는 메타데이터와 공지만으로 만들고, 표에 없는 경우는 다른 자산으로 본다(모호하면 묶지 않음).
- **관측 예외**: 정규화된 키 `BTC`·`ETH`·`SOL`·`ZEC`·`XRP`·`NEAR`·`NFT`·`LADYS`는 설계용 풀. 같은 자산의 다른 계약도 함께 설계용이 된다.
- **해시 규칙**: `sha256("D98-pool-v1|" + 키)`의 첫 바이트 짝수 → 설계용, 홀수 → 판정용.
- **제외 자산**: 스테이블·법정화폐·금 연동(M2-06 목록을 넓혀 상수로 고정: USDC, USDE, FDUSD, DAI, TUSD, PYUSD, USDD, EUR, PAXG, XAUT 등).
- **같은 자산의 계약이 동시에 여럿 활성**: 배수가 없는 계약, 없으면 가장 작은 배수 계약 하나만 쓴다. 가격·수량은 거래소 원단위 그대로 쓰고, 배수는 자산 키를 만드는 데만 쓴다(값 환산 없음).
- **출력**: 풀 목록 JSON(규칙 버전, 응답 정규화 사본, 예외·별칭·제외 표, `captured_at`, 계약별 수명·키·풀, digest)을 PR에 게시·병합한 뒤에만 설계용 풀 가격을 수집한다. 판정용 풀 가격은 2단계 사전 등록 전에 수집·조회하지 않는다.

#### 3. 신호 수식 (1단계)

시각은 UTC 밀리초, 1시간봉은 시작 시각으로 부르며 `[s, s+1h)`를 덮는다. 4시간 판단 시각을 t라 한다.
- **4시간봉**: `B_0 = [t−4h, t)`(신호봉), `B_i = [t−4h(i+1), t−4hi)`. 1시간봉 4개가 모두 있어야 만들어진다.
- **거래대금**: 분자 `A = Σ turnover(1h, 시작 ∈ [t−24h, t))`. 비교 묶음 `D_j = Σ turnover(1h, 시작 ∈ [t−24h(j+1), t−24hj))`, j = 1..30. 급증 배수 `V = A / median(D_1..D_30)`. 720개 1시간봉이 모두 있어야 하고, 중간값이 0이면 자격 없음.
- **유동성 자격·슬리피지 등급**: `mean(D_1..D_30)`로 정한다(Q30 하한·등급). 등급은 신호 시각 t에 정해 그 포지션의 진입·모든 청산과 수량 계산에 같은 값으로 쓴다. S1-B 월별 상위 4개도 같은 30개 묶음(매월 첫 00:00 기준)을 쓴다.
- **상장 경과**: `t − launch ≥ 60일` 그리고 첫 1시간봉 시작 ≤ t − 60일.
- **돌파**: 롱 `close(B_0) > max(high(B_1..B_N))`, 숏 `close(B_0) < min(low(B_1..B_N))`(신호봉 제외, 엄격 비교).
- **EMA20·ATR14 (4시간)**: 기존 지표 계약처럼 마지막 10 × n개 4시간봉 창에서 매번 다시 계산한다(EMA는 창의 첫 20개 단순평균을 씨앗으로, 계수 2/21; ATR은 기존 Wilder 정의). 연구와 실시간이 같다.
- **펀딩**: 시각 ≤ t인 마지막 정산만 쓴다(시각이 정확히 t인 정산은 이미 반영된 것으로 보고 신호보다 먼저 처리). 그 정산의 주기 = 그 정산 시각 − 바로 앞 정산 시각(기록에서 계산). 주기가 {1, 2, 4, 8}시간이 아니거나 앞 정산이 없으면 자격 없음. 8시간 환산율 = 율 × 8h / 주기. 불리함: 롱은 환산율 ≥ f, 숏은 환산율 ≤ −f. 다음 정산 시각은 쓰지 않는다.
- **BTC 추세 상태**: BTC 일봉으로 S1-B 진입 채널(설계용 연구 기본 55일, 신호일 제외 직전 55개 일봉의 최고가/최저가를 종가가 엄격히 넘을 때 LONG/SHORT로 바뀌고, 반대 돌파 전까지 유지). 초기값 FLAT, 판정 범위 시작 전 워밍업 기간에서 첫 돌파로 정해진다. 일봉 경계 00:00에는 일봉 갱신을 먼저 하고 그다음 4시간 판단을 한다. BTC는 거래 풀과 별도의 **기준 입력**이며, 그 데이터도 data_hash에 들어간다.

#### 4. 신호 연구와 진행 기준 (1단계, 설계용 풀)

- **연구 방식**: 포트폴리오·슬롯·점유·위험 한도 없이, 신호마다 **독립된 단순 거래**를 만든다. 다음 4시간봉 시가 ± 슬리피지 등급으로 진입하고, 손절은 신호 고정 절대가, 갭으로 손절을 넘어 열리면 그 시가에 청산한다. 청산은 1.2b의 추적 손절·BTC 추세 변경·최대 보유이고 테이커 수수료(0.055%) × 2, 슬리피지 등급 × 2, 실제 펀딩을 뺀다. 결과는 R 배수(순손익 ÷ 진입가에서 손절까지 위험)로 잰다. 수수료·슬리피지 등급 수치(Q30)는 이 연구 시작 전에 정한다.
- **격자**: v ∈ {2, 3}, N ∈ {42, 84}, k ∈ {2, 3}의 8개 조합. e = 3, f = 0.05%(8시간 환산), H = 42는 고정. 모든 조합을 보고한다.
- **기간**: `[2022-01-01, 2026-10-01)`, 워밍업은 그 전.
- **기술용 출력**: 신호 뒤 1·3·7일 수익 분포, 롱·숏, 연도별, 유동성 등급별, 2023-10 앞뒤.
- **진행 기준 (데이터를 보기 전에 고정, 모두 만족해야 2단계)**:
  1. 신호 수 300개 이상인 조합 중 하나 이상이 평균 순 R ≥ 0.10.
  2. 그 조합에서 R 상위 1% 거래를 빼도 평균 순 R > 0.
  3. 그 조합에서 신호 30개 이상인 해 중 과반이 평균 순 R > 0.
  4. 8개 조합 중 절반 이상이 평균 순 R > 0(특정 수치에만 기대지 않음).
- 못 넘으면 S2-M을 버리고 판정용 풀은 손대지 않은 채 남긴다. 넘어도 이 결과는 설계 참고이지 판정이 아니다.
- 구현은 연구 도구(돈이 오가는 경로 아님)이며 기본 담당은 Codex다(D86).

- **BTC 기준 상태 분리**: `reference_symbols={BTC}`와 거래 풀을 나누고, S1 거래·위험 정지가 BTC 추세 상태 계산을 멈추지 않게 한다. 지금 S2 입력 검사(종목별 S1State)를 바꾼다.

D64 종료 확인 전에는 점유 반환 없음. 위험 계산 기준(진입가/현재가에서 손절까지, 비용 포함, 이익 영역 손절은 0으로 보고 상쇄 없음). 같은 시각 S1 → S2 순서, 거절 시 다음 순위로 내려감, 기존 보유 종목 재신호는 새 슬롯이 아님, 청산 뒤 같은 봉 재진입 금지. 병렬 완료 순서가 입장 순서가 되지 않게 한다.
- **동적 종목 수명**: 진입 자격 / 시세 구독 / 관리 대상(현재 후보 ∪ 장부 ∪ 미종결 주문·손절·UNKNOWN·close intent) / 퇴역 완료를 나누고 버전·효력 시각을 저장한다. 재시작 때 장부·저널로 관리 대상을 먼저 복원한다. 새 종목 활성화 전 상품·tier·마진·레버리지·포지션 모드·시세 동기화 확인. S1 보유 상한. Symbol enum → 값 객체 이전(값 동등성·정규화·직렬화 호환, `is` 비교 제거)과 "목록에서 빠진 보유 종목 재시작 → 손절 복원 → 청산" 회귀.
- **위험 프로필(Q29 기본안)**: 거래당 위험 0.5%(D97 S1 최대 연속 손실 14회 × 1%로 낙폭 기준에 닿음), 동시 위험 합계 3%, S2 동시 포지션 4, 배분 0.6/0.4, L6 15%.
- **판정 방식(Q28)**: 설계용 풀에서 고정한 하나의 정책으로 판정용 풀 `[2022-01-01, 2026-10-01)`을 **한 번 연속 실행**한다. 목적은 고정 정책의 **다른 자산에 대한 일반화** 확인이다. 시간 기준 표본 밖이 아니므로(같은 국면·상관된 자산·반복 설계 시도) 한계로 적고 V2 데모로 보완한다. 실패 뒤 같은 판정용 풀로 다시 판정하지 않는다.
- **통과 기준 후보**: 순손익 > 0, 최대 낙폭 < 15%, 가장 큰 이익 거래 하나(비용·펀딩 포함 순손익)를 총손익에서 뺀 값 > 0, 연도 조건(Q33, 연도 손익은 청산 연도 귀속 거래 손익), S1-B·S2-M 각각 순손익 > 0, 최소 거래 수 S1-B 20·S2-M 100. 우선순위: 손실·낙폭 실패가 있으면 FAIL, 그다음 최소 거래 미달은 INDETERMINATE. 정지 뒤 처리(Q32). 내부 데이터 누락의 처리(종목 제외로 순위가 바뀌지 않게 하는 규칙).
- **고정 정책 보고서 계약**: 보고서 schema/version, 고정 매개변수, 풀·선정 정책·위험·비용 digest, PASS 근거와 운영 허용 범위. M3-01 `_validate_report`(windows[].selected)와 M3-04 D97 두 보고서 계약을 명시적으로 대체한다(가짜 window를 만들지 않음). 데모 종목 범위는 Q26과 함께.
- **계산량**: 종목별 독립 실행을 합치지 않는다(순위·위험·점유가 계좌 전체에 묶임). 풀 목록 확정 뒤 100/300/최대 풀 크기 합성 계좌(신규 상장·폐지·누락·동시 신호·잦은 손절 변경 포함)로 1년·전체 기간의 요청 수·저장·전처리/해시·최대 메모리·상세 결과 크기·재시작 시간을 잰다. 체크포인트에는 순위 시각·풀/자격 버전·BTC 상태·지표/추적·보유/예약/정지 상태가 들어간다.

## 4. V2 데모 모의투자 (D33)

- 기간: **최소 4주**. 그리고 전략별 최소 거래 수(S1 5회, S2 30회, D88)를 채울 때까지 연장한다.
- 실거래와 같은 서비스 구성으로 운영한다(Windows 서비스, Watchdog, 텔레그램, 대시보드).
- AI 효과 비교는 4.1절의 **독립 그림자 장부**로 한다.

### 4.1 AI 효과 비교: 독립 그림자 장부 (D50)

실제 계좌에 거래별 가상 결과를 붙이는 방식으로는 비교가 안 된다. AI가 진입을 한 번 막으면 이후 포지션, 평가액, 한도, 다음 진입 후보가 모두 달라지기 때문이다. 그래서 같은 시장 이벤트로 **완전히 독립된 가상 계좌 두 개**를 함께 돌린다.

| 장부 | AI | 체결 |
|---|---|---|
| `shadow_ai` | signal_id별 공유 AI 점수(`ai_scores`)를 사용 | 3.1절 가상 체결 규칙 |
| `shadow_noai` | `disabled` (전부 통과, 계수 1.0). AI 호출 없음 | 3.1절 가상 체결 규칙 |

- 두 장부는 같은 시작 평가액과 같은 설정으로 시작하고, 각자 포지션·예약·수수료·펀딩비·한도·정지 상태를 따로 가진다. 전략·위험 코드는 실제 계좌와 같은 코드를 쓴다.
- **AI 점수 (D56)**: AI 입력은 시장 정보만 쓰므로(01 2.3절) 같은 신호의 점수는 계좌와 무관하다. 점수는 **시장 신호(signal_id)마다 한 번** 만들어 `ai_scores`에 저장하고, 실제 계좌와 `shadow_ai`가 같은 값을 쓴다. 실제 계좌가 진입하지 않는 신호(정지 중, 이미 보유 등)도 점수를 만든다. 비용은 실제 계좌 단독 운영과 같다(시장 신호 수만큼).
- 어떤 신호의 점수가 없으면(AI 실패·시간 초과·비용 상한) `shadow_ai`도 실제 계좌와 같이 그 신호로 진입하지 않는다. `shadow_noai`는 점수와 관계없이 진행한다.
- 그림자 장부는 실제 계좌의 정지 상태와 무관하게 자기 상태로 계속 평가한다. M1 테스트로 고정: 실제 계좌만 HALTED인 동안에도 두 그림자 장부가 신호를 평가하고 진입한다.
- **AI 효과 판정은 `shadow_ai`와 `shadow_noai`를 비교한다.** 둘 다 같은 가상 체결 규칙을 쓰므로, 실제 체결이 없는 거절 건도 공정하게 비교된다.
- 실제 계좌와 `shadow_ai`의 차이는 **가상 체결 규칙의 정확도**를 보는 데 쓴다("백테스트와 비슷한 결과" 조건의 체결가·수수료 차이).
- 비교 지표: 수수료·펀딩비 차감 후 순손익, 최대 낙폭, 거래 수, 거래당 평균 손익(R 배수), 전략별 분해.
- D34 "AI 효과가 손해가 아님" 판정: `shadow_ai`의 순손익 ≥ `shadow_noai`의 순손익 **그리고** `shadow_ai`의 최대 낙폭 ≤ `shadow_noai`의 최대 낙폭 × (1 + 허용 폭). 허용 폭은 V2 시작 전에 이 문서에 적는다.

### 4.2 실거래로 넘어가는 조건 (D34, 모두 만족)

| 조건 | 기준 |
|---|---|
| 시스템 안정성 | 마지막 2주 동안 해결 안 된 `UNKNOWN` 주문 0건, 장부-거래소 불일치 0건, 손절 없는 포지션 0건. V0 장애 상황 중 재시작·WS 끊김은 데모에서도 한 번씩 직접 확인 |

## 5. V3 실거래 (D35: 처음부터 정한 한도로)

시작 전 준비
- **프로그램 전용 서브 계정**에서만 운영한다(D92). 개인 거래는 다른 계정에서 한다.
- Bybit 실거래 API 키: 그 서브 계정에만 발급, **출금 권한 없음**, 거래 권한만, **IP 제한 없음** (D75).
  - IP 제한이 없으므로 키가 유출되면 다른 곳에서도 거래할 수 있다. 출금 권한이 없어 자금을 빼 갈 수는 없지만, 손실을 내는 주문은 가능하다. 그래서 키는 Windows 자격 증명 관리자에만 두고(03 1장 비밀 정보), 거래소 계정에 2단계 인증을 켠다.
  - Bybit는 IP를 묶지 않은 키에 유효 기간을 둔다(발급 화면에서 기간 확인, 현재 3개월로 안내됨). 키 발급일을 기록하고, 만료 14일 전부터 텔레그램으로 매일 알린다(M3 범위). 만료되면 API 오류로 주문이 거절되므로, 그 전에 새 키로 바꾼다.
  - 나중에 고정 IP를 쓸 수 있게 되면 IP 제한 키로 바꾸는 것을 다시 검토한다.
- 데모 키와 실거래 키, `RLG_DEMO`와 `RLG_LIVE`를 섞지 않는다. 실거래 시작 시 텔레그램으로 "LIVE 시작" 알림.
- 정한 한도 수치(Q13)를 `config_versions`에 기록하고 사용자가 확인한다.

시작 후 첫 2주는 매일 확인한다
- 실제 체결가와 수수료가 데모·V1 가정과 맞는지
- 손절 주문이 모든 포지션에 걸려 있는지

데모로 되돌아가는 조건
- 해결 안 된 `UNKNOWN` 주문, 장부 불일치, 손절 누락이 한 번이라도 생기면 신규 진입을 멈추고 원인을 고친 뒤 데모에서 다시 확인한다.
- 낙폭 한도(L6)에 닿으면 HALTED. 재개 전에 원인을 검토한다.
