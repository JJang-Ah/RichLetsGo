# 검증 단계와 운영

결정 번호는 [00_DECISIONS.md](00_DECISIONS.md)를 따른다. 각 단계는 통과 조건을 **시작 전에** 기록하고, 결과를 본 뒤에 조건을 낮추지 않는다. 조건을 바꿔야 하면 이유와 날짜를 남기고 해당 단계를 처음부터 다시 한다.

## 1. 단계 개요

| 단계 | 환경 | AI | 통과하면 |
|---|---|---|---|
| V0 코드 검증 | 가상 거래소 | 가짜 응답 | V1 |
| V1 백테스트 | 과거 데이터 (SQLite) | 제외 | V2 |
| V2 데모 모의투자 | Bybit 데모 계정 + Oracle `RLG_DEMO` | 적용 | V3 |
| V3 실거래 | Bybit 실계정 + Oracle `RLG_LIVE` | 적용 | 운영 계속 |

## 2. V0 코드 검증

단위 테스트 외에 가상 거래소로 아래 상황을 재현하고, 기대 동작을 테스트로 고정한다.

| 상황 | 기대 동작 |
|---|---|
| 주문 전송 후 응답 없음 | `UNKNOWN` → orderLinkId로 조회 → 확정. 중복 주문 없음 |
| UNKNOWN 조회 결과가 부분 체결 | 체결 내역 반영 후 `PARTIALLY_FILLED`로 추적, 예약은 남은 수량 |
| UNKNOWN 주문을 계속 찾지 못함 (조회 지연·오류 포함) | 기한이 지나도 `UNKNOWN`·전체 수량 예약·신규 진입 중단 유지, 알림 |
| **조회 3종이 모두 성공·빈 결과, 포지션 일치가 여러 번 지속된 뒤 늦은 `OPEN` 도착** | 그 전까지 예약과 진입 정지가 계속 유지되어 있었음. `OPEN` 도착 후 정상 추적 |
| UNKNOWN 진입 주문에 orderLinkId 취소 성공 | 이어 오는 상태로 종결(일부 체결 반영), 남은 예약 해제 |
| UNKNOWN 진입 주문 취소에 "주문 없음" 오류 | `UNKNOWN` 유지, 예약·정지 유지 |
| 사용자 수동 `NOT_FOUND` 확정 뒤 그 주문의 체결 도착 (M3 이후) | 실제 상태로 고치고 체결 반영, 알림 |
| `CANCELLED`/`FILLED` 통지가 execution보다 먼저 도착 → 다른 계약 진입 검사 → 지연 execution | 검사 시점에 미반영 체결이 노출에 포함됨 (02 2.1절) |
| 미반영 체결이 시간 안에 안 들어옴 | 체결 내역 조회로 반영, 그동안 해당 계약 신규 진입 중단 |
| 같은 체결이 WS와 REST로 두 번 도착 | execId 중복 제거, 장부 한 번만 반영 |
| 취소 경합으로 `Filled` 두 번 도착 | 두 번째는 무시, 상태 `FILLED` 유지 |
| WS 체결이 REST 접수 응답보다 먼저 도착 | `CREATED/SUBMITTED`에서 바로 `FILLED`로 이동, 장부 정상 |
| `CANCELLED` 확정 뒤 같은 주문의 체결 도착 | 체결 반영, 상태는 `CANCELLED` 유지 |
| 부분 체결 후 취소 | 체결 수량만 장부 반영, 부착 손절 수량 = 체결 수량 |
| **진입 체결 직후, 후속 처리 전 강제 종료** | 거래소에 부착 손절이 이미 있음(가상 거래소도 Partial 손절을 체결과 동시에 생성). 재시작 후 장부가 손절과 함께 복구됨 |
| 전략 청산 시작 후 장시간(수 시간) 미복구 | 그동안 남은 수량은 원래 손절로 보호됨. 재시작 시 청산 의도대로 이어서 처리 (01 1.4절) |
| 청산 시장가(IOC)가 일부만 체결 / 거절 | 남은 수량은 손절로 보호된 채 재시도. 횟수 초과 시 해당 계약 신규 진입 중단·알림, 손절 유지 |
| 청산 확정 전 손절 취소 시도 | 일어나지 않음: 전략 보유 0이 체결 내역으로 확인된 뒤에만 손절 취소 |
| 청산과 손절이 동시에 체결되어 다른 전략까지 감소 | 초과분을 S2 → S1 순서로 장부에서 빼고, 손절 수량을 보유량에 맞추고, 알림 |
| 청산 완료 후 손절 정리 | 전략별 손절 수량 = 보유량, 계약별 합계 = 순포지션 |
| 숏 최초·추가 진입, 숏 축소, 롱 → 숏 전환 | 03 4.1절 부호 계약 표의 기대값 |
| 앱에서 직접 청산(외부 감소) | 신규 진입 중단, S2 → S1 순서로 장부 감소, 초과 손절 취소, 알림 |
| 개인 WS 끊김 중 체결 | 재연결 후 03 4.3절 동기화로 장부 복구, 그동안 신규 진입 없음 |
| REST 스냅샷 직후 손절 체결 | 버퍼링된 WS 이벤트 재생으로 반영, 안정화 확인 후에만 진입 허용 |
| 손절 수량이 보유량보다 부족 | 보호 재등록 → 실패 시 시장가 축소, 알림 |
| 프로세스 강제 종료 후 재시작 | [03_SYSTEM_ARCHITECTURE.md](03_SYSTEM_ARCHITECTURE.md) 4.3절 동기화로 복구, 정지 상태 유지 |
| Oracle 접속 끊김 | 신규 진입 중단, Watchdog 알림. **보호 작업(손절 재등록·추적 손절·청산)은 로컬 저널에 기록 후 성공**. DB 복구 후 저널 반영, 중복 없음 |
| Oracle 끊김 중 보호 주문 응답 불명 → 재시작 | 저널 반영 → orderLinkId로 UNKNOWN 해소, 중복 보호 주문 없음 |
| Oracle 끊김 중 같은 손절을 두 번 amend하고 한 번 cancel → 복구 | 저널의 작업 3건이 모두 `(operation_id, phase)` 단위로 반영되고 최종 상태가 거래소와 같음 (03 5.4절) |
| 저널에 `requested`만 쓰고 종료 | 재시작 시 작업 종류별로 거래소에서 결과 확인 후 반영 |
| 두 계약 동시 진입이 계좌 한도를 넘음 | 위험 게이트에서 하나만 통과 (02 2.1절) |
| 같은 봉 재전달 / AI 축소 후 다음 봉 | 주문 1건, 보충 주문 없음 (03 4.1절) |
| 시세 공백 / 지연 봉 | 신규 진입 중단, 공백 보충 후 재개 |
| AI 시간 초과 / 형식 오류 / 비용 상한 | 신규 진입 안 함, 손절·청산 정상 |
| 일일 한도·낙폭·연속 손실 도달 | 정해진 정지 상태와 해제 방식. HALTED `/resume`은 02 5.1절 예시대로 |
| 텔레그램 미등록 사용자 명령 | 무시하고 기록 |
| 부분 진입 → 손절로 보유 0 → 남은 진입 취소 응답 유실 또는 늦은 체결 → 새 신호 | 기존 진입 주문 종결 확정 전에는 새 에피소드 없음, 늦은 체결은 손절로 보호된 채 청산 (D64) |
| 저널 `requested` 부분 기록 실패 → 긴급 전송 성공 → 응답 유실 → 재시작 | 거래소 대조로 그 주문을 받아들임, 보호·청산 주문 중복 없음 (D65) |
| 거래일 경계 (UTC 00:00) | 기준 평가액 갱신, 일일 정지 자동 해제 |

## 3. V1 백테스트 (D32: 구간 이동 검증)

- 데이터 (D70): Bybit 공개 API의 BTCUSDT·ETHUSDT 일봉·1시간봉과 펀딩비 **최근 3년**. 1분봉은 손절·청산 사건이 겹친 구간 재검증(3.1절)에 필요한 구간만 받는다. 저장은 백테스트용 SQLite(D29).
- 방식: 예시로 12개월 구간에서 값을 정하고 다음 3개월에서 확인한다. 이를 3개월씩 옮기며 반복한다. **확인 구간 결과만** 성과로 집계한다.
- 반영 비용: 거래 수수료(지정가/시장가 구분), 슬리피지 가정, 펀딩비, 거래소 수량 단위 내림.
- 미래 정보 차단: 마감된 봉만 사용하고, S2는 그 시점의 S1 상태만 본다. 지표 계산 코드는 실거래와 같은 코드를 쓴다.
- 체결은 아래 **가상 체결 규칙**(3.1절)을 따른다.
- 결과 기록: 거래 수, 승률, 평균 손익비, 최대 낙폭, 월별 손익, 연속 손실 최대값, 전략별·계약별 분해. 이 값들이 V2의 "예상 범위" 기준이 된다.
- 통과 조건: 확인 구간 합계가 비용 차감 후 손실이 아니고, 최대 낙폭이 낙폭 한도(L6)보다 작다. 구체 수치는 V1 시작 전에 이 문서에 적는다.

### 3.1 가상 체결 규칙 (D49)

M1 가상 거래소, M2 백테스트, V2 그림자 장부(4장)가 **같은 규칙**을 쓴다. 그래야 세 곳의 결과가 같은 의미를 갖는다.

| 항목 | 규칙 |
|---|---|
| 신호 시점 | 봉 마감 시각 t의 종가로 신호를 만든다 |
| 최초 체결 가능 시점 | 다음 봉(t부터 시작하는 봉)의 시가. 신호를 만든 종가로는 체결하지 않는다 |
| 시장가 | 다음 봉 시가 ± 슬리피지(불리한 방향). 수수료는 테이커 |
| 지정가 | 이후 봉의 가격이 지정가를 **넘어서야** 체결(닿기만 하면 미체결). 체결가는 지정가, 수수료는 메이커. 유효 기간(다음 봉 마감 전)이 지나면 취소 |
| 손절(시장가 조건부) | 봉의 저가(롱)/고가(숏)가 trigger에 닿으면 발동. 체결가는 trigger ± 슬리피지. 시가가 이미 trigger를 넘어 열리면(갭) 시가 ± 슬리피지 |
| 진입 봉 안의 손절 | 진입한 봉에서 손절 가격에 닿았으면 손절된 것으로 본다(보수적) |
| 한 봉에 여러 사건 | 손절과 다른 유리한 사건(청산 신호 가격 등)이 같은 봉에서 모두 가능하면 **손절이 먼저**라고 본다 |
| 더 짧은 데이터 | 위 보수적 가정이 결과를 크게 바꾸는지 확인하려면, 해당 구간을 1분봉으로 다시 돌려 비교한다(선택, 결과 보고서에 표시) |
| 펀딩비 | UTC 00:00, 08:00, 16:00에 포지션을 들고 있으면 해당 시각 펀딩비율로 정산 |
| 수량 | 거래소 수량 단위로 내림. 최소 수량 미만이면 주문하지 않음 |
| UTC 00:00 처리 순서 | 그 시각에 마감되는 봉들은 S1(일봉) → S2(단기봉) 순서로 처리. S2는 방금 갱신된 S1 추세를 본다 |
| 같은 시각 두 계약 | BTCUSDT → ETHUSDT 순서로 위험 게이트에 넣는다(결정적 순서) |

## 4. V2 데모 모의투자 (D33)

- 기간: **최소 4주**. 그리고 전략별 최소 거래 수(V1 결과를 보고 정함)를 채울 때까지 연장한다.
- 실거래와 같은 서비스 구성으로 운영한다(Windows 서비스, Watchdog, 텔레그램, 대시보드).
- AI 효과 비교는 4.1절의 **독립 그림자 장부**로 한다.

### 4.1 AI 효과 비교: 독립 그림자 장부 (D50)

실제 계좌에 거래별 가상 결과를 붙이는 방식으로는 비교가 안 된다. AI가 진입을 한 번 막으면 이후 포지션, 평가액, 한도, 다음 진입 후보가 모두 달라지기 때문이다. 그래서 같은 시장 이벤트로 **완전히 독립된 가상 계좌 두 개**를 함께 돌린다.

| 장부 | AI | 체결 |
|---|---|---|
| `shadow_ai` | signal_id별 공유 AI 점수(`ai_scores`)를 사용 | 3.1절 가상 체결 규칙 |
| `shadow_noai` | `disabled` (전부 통과, 계수 1.0). AI 호출 없음 | 3.1절 가상 체결 규칙 |

- 두 장부는 같은 시작 평가액과 같은 설정으로 시작하고, 각자 포지션·예약·수수료·펀딩비·한도·정지 상태를 따로 가진다. 전략·위험 코드는 실제 계좌와 같은 코드를 쓴다.
- **AI 점수 (D56)**: AI 입력은 시장 정보만 쓰므로(01 2.3절) 같은 신호의 점수는 계좌와 무관하다. 점수는 **시장 신호(signal_id)마다 한 번** 만들어 `ai_scores`에 저장하고, 실제 계좌와 `shadow_ai`가 같은 값을 쓴다. 실제 계좌가 진입하지 않는 신호(정지 중, 이미 보유 등)도 점수를 만든다. 비용은 실제 계좌 단독 운영과 같다(시장 신호 수만큼).
- 어떤 신호의 점수가 없으면(AI 실패·시간 초과·비용 상한) `shadow_ai`도 실제 계좌와 같이 그 신호로 진입하지 않는다. `shadow_noai`는 점수와 관계없이 진행한다.
- 그림자 장부는 실제 계좌의 정지 상태와 무관하게 자기 상태로 계속 평가한다. M1 테스트로 고정: 실제 계좌만 HALTED인 동안에도 두 그림자 장부가 신호를 평가하고 진입한다.
- **AI 효과 판정은 `shadow_ai`와 `shadow_noai`를 비교한다.** 둘 다 같은 가상 체결 규칙을 쓰므로, 실제 체결이 없는 거절 건도 공정하게 비교된다.
- 실제 계좌와 `shadow_ai`의 차이는 **가상 체결 규칙의 정확도**를 보는 데 쓴다("백테스트와 비슷한 결과" 조건의 체결가·수수료 차이).
- 비교 지표: 수수료·펀딩비 차감 후 순손익, 최대 낙폭, 거래 수, 거래당 평균 손익(R 배수), 전략별 분해.
- D34 "AI 효과가 손해가 아님" 판정: `shadow_ai`의 순손익 ≥ `shadow_noai`의 순손익 **그리고** `shadow_ai`의 최대 낙폭 ≤ `shadow_noai`의 최대 낙폭 × (1 + 허용 폭). 허용 폭은 V2 시작 전에 이 문서에 적는다.

### 4.2 실거래로 넘어가는 조건 (D34, 모두 만족)

| 조건 | 기준 |
|---|---|
| 시스템 안정성 | 마지막 2주 동안 해결 안 된 `UNKNOWN` 주문 0건, 장부-거래소 불일치 0건, 손절 없는 포지션 0건. V0 장애 상황 중 재시작·WS 끊김은 데모에서도 한 번씩 직접 확인 |
| 백테스트와 비슷한 결과 | 최대 낙폭과 거래당 손익이 V1 예상 범위 안. 체결가 차이와 수수료가 V1 가정 이하 |
| AI 효과 | 4.1절 판정 기준을 만족(`shadow_ai`가 `shadow_noai`보다 나쁘지 않음). 나쁘면 AI 없이 실거래(`ai.mode=disabled`)할지 사용자가 따로 결정 |
| 운영 비용 | AI 월 비용이 상한(D19) 안, PC 메모리·디스크 여유 확인 |

## 5. V3 실거래 (D35: 처음부터 정한 한도로)

시작 전 준비
- Bybit 실거래 API 키: **출금 권한 없음**, 거래 권한만. 가능하면 IP 제한(가정용 IP가 바뀌면 키가 막히므로 Q20).
- 데모 키와 실거래 키, `RLG_DEMO`와 `RLG_LIVE`를 섞지 않는다. 실거래 시작 시 텔레그램으로 "LIVE 시작" 알림.
- 정한 한도 수치(Q13)를 `config_versions`에 기록하고 사용자가 확인한다.

시작 후 첫 2주는 매일 확인한다
- 실제 체결가와 수수료가 데모·V1 가정과 맞는지
- 손절 주문이 모든 포지션에 걸려 있는지

데모로 되돌아가는 조건
- 해결 안 된 `UNKNOWN` 주문, 장부 불일치, 손절 누락이 한 번이라도 생기면 신규 진입을 멈추고 원인을 고친 뒤 데모에서 다시 확인한다.
- 낙폭 한도(L6)에 닿으면 HALTED. 재개 전에 원인을 검토한다.
