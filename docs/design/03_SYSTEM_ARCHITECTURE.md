## 4. 데이터 흐름

### 4.1 진입

```
봉 마감 (공개 WS)
 → marketdata: 봉 확정·검증·저장
 → strategy: S1/S2 신호와 원래 목표 (signal_id 부여)
 → ai: 진입 신호에 대해 점수 (주기 평가 결과 + 신호 평가). AI 모드는 4.4절
 → risk 게이트 (02 2.1절, 잠금 안): 크기 계산 → 승인 목표 → 주문 수량 계산 → L1~L7 → 주문 CREATED 저장 + 예약
 → oms: 거래소 전송 (진입 주문에 손절 부착, 01 1.4절)
 → 모든 단계의 입력·결과를 decision 기록으로 남김
```

#### 원래 목표, 승인 목표, 주문 수량 (D43)

- **신호 ID** `signal_id = (전략, 계약, 봉 시작 시각, 신호 종류)`. `decisions` 테이블에서 유일 키다.
- **원래 목표**: 전략이 낸 목표 수량. **승인 목표**: AI 축소(f(s))와 위험 검사를 거친 뒤의 목표 수량. 둘 다 decision에 저장한다.
- **수량 부호 (D53)**: 목표·보유·예약·미반영 체결은 모두 **부호 있는 Decimal**로 표현한다. 롱은 +, 숏은 −. 거래소 API의 `side` + 절대 수량으로는 어댑터 경계에서만 바꾼다.
- **진입 주문 수량**: `차이 = 승인 목표 − (보유 + 예약 + 미반영 체결)` (그 전략 기준). 진입은 **승인 목표와 같은 방향으로 크기를 늘릴 때만** 낸다. 즉 `차이`와 `승인 목표`의 부호가 같고 `차이 ≠ 0`일 때 `|차이|`만큼 `sign(승인 목표)` 방향으로 진입한다. 그 밖의 경우(0, 반대 부호) 진입하지 않는다.
- 크기를 줄이는 것은 진입 계산으로 하지 않는다. 축소·청산은 01 1.4절 청산 절차로만 한다.
- **방향 전환**: 한 주문으로 0을 넘어가지 않는다. 기존 방향의 청산이 체결 내역으로 확정된 뒤(보유 0), 반대 방향 신호를 새 진입으로 처리한다.
- M1 인터페이스·테스트 기대값 (그 전략 기준, 예약·미반영 0 가정):

  | 상황 | 보유 | 승인 목표 | 결과 |
  |---|---|---|---|
  | 숏 최초 진입 | 0 | −1 | 매도 1 진입 |
  | 숏 추가 진입 | −1 | −1.5 | 매도 0.5 진입 |
  | 숏 목표 축소 | −1.5 | −1 | 진입 없음 (축소는 청산 절차) |
  | 롱 → 숏 전환 | +1 | −1 | 진입 없음. 롱 청산 확정(보유 0) 후 다음 평가에서 매도 1 진입 |
  | 롱 최초 진입 | 0 | +1 | 매수 1 진입 |
- 같은 signal_id가 다시 들어오면(같은 봉 재전달, 재시작 후 재처리) 새로 평가하지 않고 저장된 decision을 그대로 쓴다. 그래서 중복 주문이 생기지 않는다.
- 승인 목표는 그 신호가 살아 있는 동안 고정이다. AI가 0.5배로 줄였다면 다음 봉에서 원래 목표와의 차이를 보충하지 않는다.
- 거절(AI 문턱 미달, 위험 한도)된 신호는 같은 signal_id로 다시 평가하지 않는다. 다음 봉에서 전략이 다시 진입 신호를 내면 그것은 새 signal_id로 새로 평가한다.
- 진입 주문이 일부만 체결되고 나머지가 취소·만료되면 그 신호는 체결된 만큼으로 끝난다. 나머지를 다시 주문하지 않는다.
- 진입 지정가 주문의 유효 기간은 다음 봉 마감 전까지로 한다(그 이후는 취소).
- M1 테스트로 고정: (a) 같은 봉 재전달 시 주문 1건, (b) AI 0.5배 축소 후 다음 봉에서 보충 주문 없음, (c) 부분 체결 후 취소된 신호에 추가 주문 없음.

### 4.2 체결과 동기화

```
개인 WS (주문·체결·포지션)
 → oms: 주문 상태 갱신, 체결 저장 (5장 규칙)
 → portfolio: 전략 장부 갱신
 → risk: 평가액·손실·연속 손실 갱신 → 필요하면 정지 상태 변경
 → notify: 체결·정지 알림
```

- 개인 WS가 끊기면 신규 진입을 멈추고, 재연결 시 4.3절의 **동기화 절차**를 그대로 실행한다.
- 일정 간격(예: 1분)으로 REST 조회와 장부를 비교하는 정기 대조도 돌린다.

### 4.3 시작·재연결 동기화 (D47)

REST로 상태를 읽는 사이에 체결이 일어나도 놓치지 않도록, **개인 WS를 먼저 구독하고 이벤트를 쌓아 둔 뒤** REST 스냅샷을 읽는다.

1. 설정·비밀 정보 로딩, 환경 확인 (live이면 시작 시 텔레그램으로 알림)
2. Oracle 접속, 마이그레이션 버전 확인 (맞지 않으면 시작 중단). 로컬 저널(5.3절)이 있으면 DB에 먼저 반영
3. 저장된 정지 상태 복원. 이 시점부터 동기화가 끝날 때까지 `ENTRY_PAUSED_SYSTEM(sync)`
4. 개인 WS 구독 시작. 들어오는 이벤트는 처리하지 않고 버퍼에 쌓는다
5. REST 스냅샷: 잔고, 포지션, 미체결 주문(조건부 주문 포함), 그리고 **마지막으로 저장한 체결 시각 − 여유 시간(예: 10분)부터 현재까지의 체결 내역**
6. 스냅샷 반영: 놓친 체결 저장(execId 중복 제거), 주문 상태 확정(5장 규칙), 장부 재계산
7. 버퍼에 쌓인 WS 이벤트 재생 (같은 규칙이라 중복이어도 안전)
8. 보호 확인: 전략별 손절 수량 = 보유량인지 확인, 모자라면 손절 등록(5.4절 보호 작업), 남는 손절은 취소. 미완료 청산 의도(01 1.4절)가 있으면 이어서 실행
9. 안정화 확인: 포지션을 REST로 한 번 더 읽어 장부와 일치하는지 본다. 다르면 5로 돌아간다(일정 횟수 넘으면 알림 후 정지 유지)
10. 시세 WS 연결, 필요한 과거 봉 보충
11. `ENTRY_PAUSED_SYSTEM(sync)` 해제. 다른 정지 상태가 없으면 신규 진입 허용

- 마지막 체결 시각이 체결 내역 API의 조회 가능 범위보다 오래됐으면 자동 복구하지 않고, 정지 상태로 두고 알린다(사람이 확인).

### 4.4 AI 모드 (D51)

| 모드 | 동작 | 허용 환경 |
|---|---|---|
| `disabled` | AI를 부르지 않는다. 모든 신호를 통과로 보고 계수 1.0. decision에 `ai_mode=disabled` 기록 | backtest, demo. live는 D34에서 사용자가 "AI 없이 실거래"를 결정한 경우에만 |

## 5. 주문 상태 (D44)

신규 노출 주문은 거래소에 보내기 **전에** DB에 저장하고, 우리 쪽 주문 ID(`orderLinkId`)를 붙인다. 응답이 늦거나 끊겨도 이 ID로 거래소에 조회해 중복 주문을 막는다. orderLinkId는 36자 이하로 만들고, 형식에 환경·전략·용도를 넣는다(예: `D-S2-E-<짧은 고유값>`; 용도 E=진입, X=청산, P=보호 재등록).

```
CREATED ──전송──→ SUBMITTED ──접수──→ OPEN ──일부 체결──→ PARTIALLY_FILLED
   │                 │                                       │
   │                 │ 응답 없음/시간 초과                      ├──→ FILLED
   │                 ▼                                       └──→ CANCELLED (일부 체결 포함)
   │              UNKNOWN ──조회──→ OPEN / PARTIALLY_FILLED / FILLED / CANCELLED / REJECTED / EXPIRED
   │                 │        └── 찾지 못함 → UNKNOWN 유지, 재조회 (기간 초과 시 알림·수동 확인)
   │                 └── 부재 확정 조건(5.3절)을 모두 만족 → NOT_FOUND
   └──→ ABORTED (전송 전 위험 검사 실패나 정지)
```

### 5.1 상태 전이 규칙

- 상태에는 순서가 있다: `CREATED < SUBMITTED < UNKNOWN < OPEN < PARTIALLY_FILLED < 종결`. 종결 상태는 `FILLED`, `CANCELLED`, `REJECTED`, `EXPIRED`, `NOT_FOUND`, `ABORTED`.
- **앞으로만 간다.** 이벤트가 현재보다 뒤 상태를 알려 주면 중간 단계를 건너뛰어 바로 간다(WS 체결이 REST 접수 응답보다 먼저 와도 정상 처리). 현재보다 앞 상태를 알려 주는 이벤트는 기록만 하고 상태는 바꾸지 않는다.
- **종결 상태는 바꾸지 않는다.** 예외는 둘이다.
  - `CANCELLED`로 확정된 뒤 같은 주문의 체결이 새로 들어오면, 체결은 반영하고 상태는 그대로 둔다(누적 체결 수량만 늘어난다).
  - `NOT_FOUND`로 확정된 주문의 체결이나 주문 이벤트가 나중에 들어오면, **실제 상태로 고치고**(유일하게 허용되는 종결 상태 변경) 체결을 반영하며 즉시 알린다. 이 이력은 `order_events`에 남긴다.
- 체결(execution)은 주문 상태와 관계없이 **항상** 반영한다(5.2절).
- 취소 경합: Bybit는 취소 요청이 접수될 때 `Filled`를 두 번 보낼 수 있다. 같은 상태 이벤트가 반복되면 무시한다.
- 상태가 바뀔 때마다 `order_events`에 한 줄씩 추가한다(덮어쓰지 않음). 무시한 이벤트도 원문을 남긴다.

### 5.2 체결 반영 규칙

- 장부는 **체결(execution) 이벤트로만** 바꾼다. 주문 상태 메시지의 누적 수량으로 장부를 바꾸지 않는다.
- `fills.exec_id`는 유일 키다. 이미 있는 execId는 무시한다(WS·REST 중복, 재생 모두 안전).
- 체결 저장, 주문 누적 체결 수량 갱신, 전략 장부 갱신, 예약 → 보유 이동은 **DB 트랜잭션 하나**로 한다.
- 주문마다 두 값을 따로 저장한다: **장부 반영 체결 수량**(저장된 체결 합계)과 **거래소 누적 체결 수량**(주문 이벤트·조회로 받은 최댓값). 차이는 미반영 체결로 노출에 계속 포함한다(02 2.1절). 차이가 정해진 시간 안에 사라지지 않으면 그 주문의 체결 내역을 조회해 반영한다.

### 5.3 UNKNOWN 해소

1. orderLinkId로 미체결 주문 조회
2. 없으면 주문 이력 조회
3. 그래도 없으면 전송 시각 이후 체결 내역에서 orderLinkId 검색
4. 그래도 없으면 `UNKNOWN`을 유지하고 간격을 늘려 다시 조회한다.
- 조회 결과가 `PARTIALLY_FILLED`일 수 있다. 이 경우 체결 내역을 받아 5.2절대로 반영하고 남은 수량은 계속 추적한다.
- `UNKNOWN`인 동안: 해당 계약의 신규 진입을 멈추고, 전체 수량을 예약으로 잡는다(02 2.1절).
- **기한(예: 10분)은 부재 확정 근거가 아니다.** 기한이 지나면 알림을 보내고 수동 확인 대상으로 표시할 뿐, `UNKNOWN`·예약·진입 정지는 그대로 유지한다. Bybit 조회 결과는 비동기 처리로 늦게 보일 수 있기 때문이다.

**`NOT_FOUND` 확정 조건 (D54, 모두 만족)**
- (a) 전송 후 최소 대기 시간(예: 5분)이 지났다.
- (b) 1~3의 조회가 **모두 오류 없이 성공**했고 어디에도 그 orderLinkId가 없다. 조회 오류·시간 초과가 하나라도 있으면 이번 확인은 무효다.
- (c) 그 계약의 거래소 포지션 크기가 장부(보유 + 다른 주문의 미반영 체결)와 일치한다. 설명되지 않는 노출이 없다.
- (d) (a)~(c)를 일정 간격(예: 2분)을 두고 **두 번 연속** 만족했다.
- 만족하면 `NOT_FOUND`로 확정하고 예약을 해제한다. 사용자가 수동 확인 후 텔레그램으로 확정할 수도 있다(명령 추가는 M3에서 결정, 그 전에는 위 조건으로만 확정).
- 확정 뒤에도 그 주문의 이벤트가 들어오면 5.1절 예외대로 실제 상태로 고치고 반영한다.

### 5.4 DB 장애 중 보호 작업 (D45)

주문을 두 종류로 나눈다.

| 종류 | 예 | DB가 안 될 때 |
|---|---|---|
| 노출 증가 | 진입 | 보내지 않는다 (DB 선기록 필수) |
| 보호·축소 | 손절 재등록, 추적 손절 수정, 전략 청산, 위험 축소 | **로컬 저널에 먼저 기록**하고 보낸다 |

- 로컬 저널: `data/journal/`의 추가 전용 JSON Lines 파일. 한 줄 쓸 때마다 flush + fsync.
- **저널 레코드 (D55)**: 주문 ID와 작업 ID를 구분한다. 같은 손절을 여러 번 수정·취소해도 각각 별개의 작업이다.

  | 필드 | 내용 |
  |---|---|
  | `operation_id` | 작업마다 새로 만드는 고유 ID (UUID) |
  | `phase` | `requested` (보내기 직전) / `result` (응답 받은 뒤) |
  | `seq` | 저널 안 순번 (재생 순서) |
  | `op_type` | `create` / `amend` / `cancel` / `close` |
  | `target` | 대상 주문의 orderLinkId 와 거래소 orderId (create는 새 orderLinkId) |
  | `request` | 보낸 내용 (amend는 이전 값과 새 trigger 가격) |
  | `result` | 응답 코드·내용 (`result` 단계만) |
  | `ts` | 시각 |
- 저널 기록마저 실패하면(디스크 오류) **보호 작업은 그래도 보낸다**. 거래소 상태가 기준이고 orderLinkId 형식(용도 P/X)으로 나중에 찾을 수 있기 때문이다. 이 경우 즉시 알린다.
- **재생**: DB가 복구되거나 프로세스가 재시작되면 저널을 `seq` 순서로 `protective_operations` 테이블에 반영한다. 중복 판단은 `(operation_id, phase)` 단위로 한다(이미 있으면 건너뜀). orderLinkId로 건너뛰지 않는다.
- `requested`만 있고 `result`가 없는 작업(보내기 직전·직후 종료)은 결과를 거래소에서 확인한다.
  - `create`: orderLinkId로 5.3절 조회
  - `amend`: 대상 주문의 현재 trigger 가격을 읽어 요청 값과 비교
  - `cancel`: 대상 주문의 현재 상태 확인
  - `close`: 해당 orderLinkId로 5.3절 조회와 체결 내역 확인
- 그다음 4.3절 동기화로 거래소와 전체를 대조한다.
- 반영이 끝난 저널 파일은 보관 폴더로 옮긴다.

### 5.5 주문 종류

진입(지정가/시장가, 손절 부착), 손절(진입에 부착되어 거래소가 생성, 또는 보호 재등록), 청산(reduce-only 시장가). 거래소 익절 주문은 쓰지 않는다(01 1.4절). 주문마다 소속 전략을 기록한다.

| `fills` | 체결 ID(exec_id, 유일 키), 주문, 전략, 가격, 수량, 수수료, 체결 시각 |
