# 위험 관리 정책

대상: Bybit USDT 무기한 BTCUSDT, ETHUSDT. 결정 번호는 [00_DECISIONS.md](00_DECISIONS.md), 전략은 [01_STRATEGY_AND_AI.md](01_STRATEGY_AND_AI.md)를 따른다.

숫자(X%, N회 등)는 모두 설정값이다. 이 문서는 구조와 동작만 정하고, 값은 백테스트·모의투자를 보고 사용자가 정한다.

## 1. 기본 정의

| 용어 | 정의 |
|---|---|
| 통화 | 모든 한도는 USDT로 정한다 (D20). 원화 목표는 설정할 때 한 번 환산해 적고, 실행 중에는 환율을 쓰지 않는다. |
| 평가액 (equity) | 거래소가 보고하는 USDT 지갑 잔고 + 미실현 손익. 내부 계산이 아니라 거래소 값을 기준으로 한다. |
| 거래일 | UTC 00:00 ~ 다음 UTC 00:00 (한국 시간 오전 9시 기준). |
| 일일 손실 | 거래일 시작 시 평가액 − 현재 평가액 (실현 + 평가 손익, D21). 입출금은 차감해서 계산한다. |
| 최고점 대비 낙폭 | **위험 기준 최고점** 대비 현재 평가액의 하락 비율 (D24). 입출금은 최고점에 반영한다. |
| 기록용 최고점 | 운영 시작 이후 평가액의 실제 최고값. 성과 보고용이며 절대 낮추지 않는다. |
| 위험 기준 최고점 | L6 검사에 쓰는 최고점. 평소에는 기록용 최고점과 같고, HALTED 재개 때만 현재 평가액으로 재설정된다(5장, D48). |
| 노출 | 계약별 보유 + 예약 + 미반영 체결의 명목 금액 (2.1절) |

## 2. 한도 계층

주문은 아래 검사를 **모두** 통과해야 나간다. 하나라도 걸리면 거절하고 이유를 기록한다.

| 단계 | 한도 | 기준 | 걸렸을 때 |
|---|---|---|---|
| L1 거래당 위험 | 손절 시 손실 ≤ 평가액 × r% (D22) | 진입 직전 평가액 | 크기를 줄인다. 최소 주문 수량보다 작아지면 진입하지 않는다. |
| L2 계약별 노출 | 계약별 노출 ≤ 설정값 | 보유 + 예약 + 미반영 체결 (2.1절) | 거절 |
| L3 계좌 노출 | 전체 노출 ≤ 설정값, 레버리지 ≤ 상한 (D11) | 보유 + 예약 + 미반영 체결, 레버리지는 거래소 설정값 확인 | 거절 |
| L4 전략별 일일 한도 | 전략 일일 손실 ≤ 계좌 일일 한도 × 전략 비율 (D23) | 전략 장부 | 해당 전략만 그날 신규 진입 중단 |
| L5 계좌 일일 한도 | 일일 손실 ≤ 설정값 (D7 범위) | 평가액 | 모든 전략 그날 신규 진입 중단 |
| L6 최고점 대비 낙폭 | 낙폭 ≤ X% | 평가액 | 모든 전략 정지, 수동 재개 필요 |
| L7 연속 손실 | 전략별 연속 손절 N회 | 전략 장부 | 해당 전략만 T시간 신규 진입 중단 (D26) |

공통 규칙
- 신규 진입만 막는다. **손절 주문과 청산은 어떤 상태에서도 막지 않는다.**
- 포지션을 줄이는 주문은 L1~L3 노출 한도에서 면제한다 (REVIEW.md 발견 1 반영).
- 전략 비율(D23)의 기본값은 설정으로 받는다(예시: S1 60%, S2 40%). L1의 r%도 전략별로 둘 수 있다.

### 2.1 위험 게이트: 검사와 예약을 한 번에 (D46)

노출을 늘리는 주문은 모두 계좌 단위 **위험 게이트** 하나를 차례로 통과한다. 두 계약의 진입이 같은 상태를 동시에 읽고 둘 다 통과하는 일을 막기 위해서다.

- 게이트는 계좌당 하나의 asyncio 잠금으로 보호한다. 잠금 안에서는 (1) 현재 보유·예약 읽기, (2) L1~L7 검사, (3) 통과 시 주문을 `CREATED`로 DB에 저장하면서 예약 생성까지 한다. 잠금 안에서 거래소 호출이나 AI 호출은 하지 않는다(AI 점수는 게이트에 들어오기 전에 받는다).
- 예약 명목 금액 = 남은 수량 × 보수적 가격(지정가 주문은 지정가, 시장가 주문은 기준가 × (1 + 슬리피지 여유)).
- 노출은 주문마다 세 부분으로 나눠 계산한다 (D52).

  | 부분 | 수량 | 언제 사라지나 |
  |---|---|---|
  | 보유 | 장부에 반영된 체결(execution) 합계 | 청산·손절 체결 |
  | **미반영 체결** | 거래소가 알려 준 누적 체결 수량 − 장부에 반영된 체결 합계 (0 이상) | 해당 execution이 장부에 반영될 때 |
  | 예약 | 주문 수량 − 거래소 누적 체결 수량 | 주문이 종결 상태로 확정될 때 (UNKNOWN은 03 5.3절의 확정 조건을 만족할 때까지 전체 수량 유지) |

- 그래서 `CANCELLED`나 `FILLED` 통지가 execution보다 먼저 와도, 이미 체결된 수량은 "미반영 체결"로 노출에 남는다. 종결 확정 때 해제하는 것은 **체결되지 않은 남은 수량**뿐이다.
- 미반영 체결이 정해진 시간(예: 30초) 안에 execution으로 들어오지 않으면 체결 내역 API로 그 주문의 체결을 조회해 반영한다. 반영될 때까지 해당 계약의 신규 진입을 멈춘다.
- 응답이 불분명한 주문(`UNKNOWN`)은 전체 수량이 체결될 수 있다고 가정한다.
- 프로세스 재시작 시 예약은 DB 주문 상태에서 다시 계산한다(메모리 값은 믿지 않는다).
- M1 테스트로 고정 (숫자는 예시):
  - 남은 계좌 한도 100 USDT에서 BTC 80, ETH 80 진입 의도가 동시에 들어오면 하나만 통과하고 다른 하나는 거절된다.
  - BTC 주문 1 중 0.4 체결 → `CANCELLED` 통지 먼저 도착 → ETH 진입 검사 → 지연 execution 도착. ETH 검사 시점에 BTC 0.4가 노출에 포함돼 있어야 한다. `FILLED` 선도착도 같은 방식으로 확인한다.

## 3. 포지션 크기 계산

```
허용 손실   = 평가액 × r% (L1) × AI 축소 계수 f(s) (D15, 0.5~1.0)
손절 거리   = |진입 예상가 − 손절가| + 예상 슬리피지 + 왕복 수수료(가격 환산)
수량        = 허용 손실 ÷ 손절 거리  → 거래소 수량 단위로 내림
증거금      = 수량 × 진입가 ÷ 레버리지
```

- 레버리지는 증거금 크기만 정한다. 수량(위험)은 손절 거리로 정한다 (P5).
- 진입 전 예상 강제청산 가격을 계산해, 손절가가 강제청산가보다 설정 비율 이상 안쪽일 때만 진입한다 (P5).
- 내림한 수량이 거래소 최소 주문 수량보다 작으면 진입하지 않는다(최소 수량으로 올리지 않는다).

## 4. 운영 중 보호 장치

| 상황 | 동작 |
|---|---|
| 시세 끊김 / 최신 봉 지연 | 신규 진입 중단. 복구 후 데이터 공백을 확인하고 재개. |
| 거래소 API 오류 반복 | 신규 진입 중단, 알림. 주문 상태는 재조회로 확인. |
| 장부와 거래소 포지션 불일치 | 신규 진입 중단, 알림. 거래소 값을 기준으로 맞추고 차이를 기록. |
| 손절 주문이 확인되지 않은 포지션 | 즉시 손절 재등록 시도. 실패하면 해당 포지션을 시장가로 줄이고 알림. |
| AI 실패 / 시간 초과 / 월 비용 상한 | 신규 진입 중단 (P2, D19). 손절·청산은 계속. |
| 프로그램 재시작 | 거래소 상태로 장부 복구 → 손절 주문 확인 → 정지 상태 복원 → 재개. 정지 상태는 디스크에 저장해서 재시작해도 풀리지 않게 한다. |
| 프로그램 무응답 | 별도 감시 프로세스가 텔레그램으로 알림 (P1). |

## 5. 정지 상태

```
RUNNING
 ├─ L4/L7 → STRATEGY_PAUSED(전략, 이유, 해제 시각)  → 자동 해제 (다음 거래일 / T시간 후)
 ├─ L5    → ENTRY_PAUSED_DAILY                     → 다음 거래일 UTC 00:00 자동 해제 (D25)
 ├─ 운영 보호 장치(4장) → ENTRY_PAUSED_SYSTEM(이유) → 원인이 해소되면 자동 해제
 ├─ 텔레그램 /pause → ENTRY_PAUSED_MANUAL          → /resume 으로만 해제
 └─ L6    → HALTED                                 → /resume 으로만 해제 (D25)
```

- 여러 정지 상태가 겹치면 모두 해제돼야 신규 진입이 가능하다.
- 상태가 바뀔 때마다 텔레그램으로 알리고 기록한다.

### 5.1 HALTED 재개 (D48)

정지 플래그만 지우면 낙폭이 그대로라서 다음 검사에서 바로 다시 HALTED가 된다. 그래서 HALTED의 `/resume`은 **위험 기준 재설정**을 함께 한다.

1. `/resume` 수신 → 봇이 현재 상태와 재설정 내용을 보여 주고 재확인을 요청한다. 예: "기록용 최고점 100, 현재 평가액 80, 낙폭 20%. 위험 기준 최고점을 80으로 재설정하고 재개합니다. 다음 정지는 72(한도 10%)입니다. 진행할까요?"
2. 재확인 응답 → 위험 기준 최고점 = 현재 평가액, HALTED 해제. 기록용 최고점(100)은 그대로 둔다.
3. 재설정 이력(시각, 이전·이후 값, 명령 보낸 사람)을 `risk_states`에 남긴다.

- `ENTRY_PAUSED_MANUAL`만 걸려 있을 때의 `/resume`은 재설정 없이 수동 정지만 해제한다.
- 둘 다 걸려 있으면 한 번의 재확인으로 둘 다 처리하되, 재확인 메시지에 재설정 내용을 반드시 보여 준다.
- M1 테스트로 고정: 최고점 100, 평가액 80, 낙폭 한도 10%에서 (a) 재확인 없이 `/resume` → HALTED 유지, (b) 재확인 후 → 위험 기준 80, 기록용 100, 진입 허용, (c) 이후 평가액 72 → 다시 HALTED (숫자는 예시).

## 6. 텔레그램 명령 (D27)

| 명령 | 동작 | 확인 단계 |
|---|---|---|
| `/status` | 포지션, 오늘 손익, 한도 사용률, 정지 상태, 마지막 신호·AI 호출 시각 | 없음 |
| `/pause` | 신규 진입 중단 (ENTRY_PAUSED_MANUAL) | 없음 |
| `/resume` | 수동 정지 해제. HALTED는 위험 기준 최고점 재설정과 함께 해제 (5.1절) | 재확인 메시지에 응답해야 실행 |
| `/cancel` | 미체결 **진입** 주문 취소. 손절 주문은 유지 | 재확인 메시지에 응답해야 실행 |
| `/resolve <orderLinkId>` | `UNKNOWN` 주문을 사용자가 Bybit에서 직접 확인한 뒤 `NOT_FOUND`로 확정 (03 5.3절, D54). M3에서 구현 | 재확인 메시지에 응답해야 실행 |

- 미리 등록한 텔레그램 사용자 ID에서 온 명령만 처리한다. 그 외 메시지는 무시하고 기록한다.
- 봇 토큰은 다른 API 키와 같은 방식으로 로컬에 보관한다.
- **전체 청산 명령은 두지 않는다.** 긴급하게 전부 청산해야 하면 Bybit 앱에서 직접 한다. 청산 후 프로그램은 재시작 절차처럼 거래소 상태로 장부를 맞춘다.
