# 개발 방식

결정 번호는 [00_DECISIONS.md](00_DECISIONS.md)를 따른다.

## 1. 역할 (D37)

| 역할 | 담당 | 하는 일 |
|---|---|---|
| 결정 | 사용자 | 설계 결정, 한도 수치, PR 병합, 실거래 전환 |
| 설계·검토 | Claude Code | 설계 문서 작성·수정, 작업 명세 작성, PR이 설계와 맞는지 검토 |
| 구현 | Codex | 작업 명세에 따라 코드·테스트 작성, PR 생성 |

- 설계 문서(`docs/design/`)가 기준이다. 구현 중 설계와 다르게 해야 할 이유가 생기면 Codex는 코드를 바꾸기 전에 PR이나 HANDOFF.md에 질문으로 남기고, Claude가 설계 문서를 먼저 고친다.
- 검토자는 구현자와 항상 다르다. 급한 수정도 같다.

## 2. 작업 흐름 (D38)

```
1. Claude: 마일스톤을 작업 단위로 나눠 작업 명세 작성 (docs/tasks/Mx-yy.md)
2. 사용자: 명세 확인
3. Codex: 브랜치 생성 → 구현 → 테스트 → PR (명세 번호 포함)
4. CI: 테스트 자동 실행
5. Claude: 설계·명세 대비 검토, 발견 사항을 PR 코멘트로
6. Codex: 수정
7. 사용자: 병합
8. 구현자: HANDOFF.md에 변경·검증·남은 작업 기록
```

규칙
- `main`에 직접 커밋하지 않는다. 문서 수정도 PR로 한다.
- 브랜치 이름: `design/…`(설계 문서), `task/M1-03-risk-engine`(구현), `fix/…`(수정).
- PR 하나는 작업 명세 하나. 크기는 검토 가능한 정도로 작게 유지한다.
- CI가 실패한 PR은 병합하지 않는다.
- 두 AI 사이의 연락은 PR 코멘트와 `docs/HANDOFF.md`로 한다. 자동 메시지 전달은 없다.

### 작업 명세 형식

```markdown
# M1-03 위험 엔진 L1~L3
- 근거: 02_RISK_MANAGEMENT.md 2장, 3장
- 범위: 만들 것 / 만들지 않을 것
- 인터페이스: 함수·클래스 시그니처
- 완료 조건: 통과해야 할 테스트 목록
- 검토 포인트: 검토자가 특히 볼 것
```

- KIS 국내·미국 주식은 V3 실거래가 안정된 뒤 별도 설계로 시작한다(D5).

## 4. 기존 코드 (D39)

- `trading_lab/`은 새 패키지로 대체하고 삭제한다.
- 기존 검증 아이디어(통화 일치, Decimal 강제, reduce-only 방향 검사, 레버리지로 위험을 줄이지 않음)는 M1 위험 엔진 테스트로 옮긴다.
- REVIEW.md 발견 1~9는 M0·M1 작업 명세에 반영하고, 반영 여부를 REVIEW.md에 표시한다.

## 5. 코드 기준

- Python: 운영은 이 PC의 3.14, 최소 지원은 3.12 (D40). 이 PC에서는 3.14로 가상환경(`.venv`)을 만든다. 3.13 이상에서만 되는 문법·표준 라이브러리 기능은 쓰지 않는다. CI가 두 버전 모두에서 확인한다.
- 금액·가격·수량은 `Decimal`. `float`는 지표 계산 내부에서만 쓰고, 주문으로 넘어가기 전에 Decimal로 바꾼다.
- 시각은 timezone 정보가 있는 UTC `datetime`.
- 전략·위험·장부는 외부 연결 없는 순수 로직(03_SYSTEM_ARCHITECTURE.md 3장).
- 비밀 정보는 코드·설정·로그·테스트 데이터에 넣지 않는다.
- 새 외부 패키지는 PR 설명에 이유를 적는다.
