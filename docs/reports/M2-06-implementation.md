# M2-06 구현 검증 기록

이 기록은 합성 검증과 메타데이터 선정 결과다. D97 사전 등록이나 실제 성과 판정이 아니다.

## 선정

[선정 결과](D97-universe.md): SOLUSDT, ZECUSDT, XRPUSDT, NEARUSDT. 메타데이터를 1회 수집했고 가격 봉·펀딩 이력은 수집하지 않았다. 종목은 교체하지 않는다. 결과 본문 해시 `a60b6429fb9c580175d990a8fba68bc323ec106f789ece8b5a0822624086152d`.

## 구현 계약

- `[backtest] symbols`는 비어 있지 않고 중복이 없어야 하며 실행 때 심볼 이름순으로 정렬한다. 기존 설정에서 이 항목이 없으면 BTC·ETH 연구로 해석해 과거 계약을 보존한다. 신규 종목 identity에는 `symbols`를 기록한다. 기존 BTC·ETH manifest/산출물 형식은 유지한다.
- `S1B` 격자는 내부적으로 `(S1, None)` 쌍이며 보고서 `selected`는 `[S1 매개변수, null]`이다. S2 분해는 `{}`, S2 신호·주문 없음, S1 위험 배분은 0.6 그대로다. M3-04 로더 확장은 후속 작업이다.
- 부 판정의 `min_strategy_net_pnl_usdt`는 identity에 포함하며 엄격한 `>`를 사용한다. 합계 손익·낙폭을 통과해도 S2 순손익이 0 이하면 FAIL이다.
- 신규 종목 구간 입력 검사는 학습·워밍업·확인 범위 전체에 적용한다. 후보가 없어도 확인 범위의 누락은 INVALID_DATA로 표시해 두 판정의 무효 구간을 맞춘다.
- `backtest.paired`가 두 캠페인을 먼저 준비하고 동일 data_hash를 확인한다. 최초 준비 호출로 성과를 계산하지 않는다. 준비된 두 manifest를 게시한 뒤 동일 인수로 계산을 호출한다. 같은 캠페인은 기존 실행기의 해시 기반 재개를 사용한다.
- 준비 실패는 두 판정 모두 INVALID_INPUT이다. `pairs/<identity>/pair.json`, 요약 `report.md`, 실패 시점 SQLite 스냅샷을 보존한다. 이 스냅샷의 파일 해시는 누락 상품/tier 때문에 계산할 수 없는 정상 data_hash와 구분한다. 실패 기록은 동일 등록에서 재계산하지 않는다. 최종 실패 JSON/보고서를 `docs/reports/`로 게시하는 것은 실제 실행 절차에서 수행한다.
- 수집 CLI `--until`은 데이터 종료 경계이며 상품/tier의 captured_at는 실제 수집 시각이다. 사전 등록을 사용하는 수집은 요청 시도 번호·UTC 시각을 수집 기록에 남긴다. 이 기록까지 고정한 뒤 두 캠페인을 준비한다. 재시도 여부가 다른 수집의 전체 data_hash가 같다고 가정하지 않는다.

4종목 합성 2026년 12개월, 단일 프로세스, S1-B(55,20), 부 판정 S2-P(2,20,14,1.5,2,30):

| 모드 | 초 | 최대 working set MiB | 상태 |
| --- | --- | --- | --- |
| S1 단독 | 22.556 | 144.57 | COMPLETED |
| S1×S2 | 125.706 | 173.68 | COMPLETED |

[주 측정 JSON](M2-06-synthetic-primary.json), [부 측정 JSON](M2-06-synthetic-secondary.json). 이 합성 경로에서는 두 모드 모두 32거래/64주문이다. S2 신호 평가 비용을 포함하지만 실제 시장의 체결 빈도나 모든 주문 부하를 대표하는 표본은 아니다. S2·복구·손절 동작은 별도 기존/신규 회귀에서 검증한다.

학습 주 28회·부 224회, 확인 각각 최대 14회. 12개월 환산 주 31.5회·부 227.5회. workers=4, 효율=0.8이면 약 0.062h + 2.482h = **2.544h** 예상이다. 두 초안 설정에 모드별 측정을 반영했고 캠페인별 6시간 상한은 등록 전 계획 값이다. 실제 판정 시 속도로 재추정한다.

병합 기준 `e08bf48`과 변경 코드에 같은 BTC·ETH 합성 72시간 입력·정책을 넣어 비교한 결과는 모두 COMPLETED이고 해시는 `216ccaad77ab85c246e417aa8515298aab04ba602539f3207d6f7d9b9209a075`로 같았다. 실제 BTC·ETH 자료를 재판정하지 않았다.

## Claude 검토 뒤 실행 순서

1. 구현 검토·병합 후 코드 커밋, 선정 해시, 두 설정 전체, 수집 범위·비용·한계를 사전 등록해 게시한다.
2. 사전 등록 파일 형식은 `{"body": {...}, "sha256": "codec.digest(body)"}`이다. body에는 `id`, `symbols` 배열, `collection.start`/`collection.end_exclusive` UTC 문자열과 두 설정 전체를 넣는다. 수집에는 `--preregistration` 경로를 전달하고 각 캠페인 설정에는 동일 `[backtest.preregistration] id/sha256`을 넣는다. 등록 게시 자체는 사람의 검토 절차이며 로더가 GitHub 게시 여부까지 인증하는 것은 아니다.
3. 지정한 범위의 4종목 일봉·시간봉·펀딩을 한 번 수집한다. `--until 2026-10-01T00:00:00Z`를 지정한다. 일시적 오류의 동일 범위 재시도는 기록한다.
4. `python -m richletsgo.backtest.paired --primary <주 설정> --secondary <부 설정> --commit <등록 커밋> --prepare-only`로 고정하고 두 manifest와 pair.json을 게시한다.
5. 게시 후 같은 인수에서 `--prepare-only`만 제거해 주→부를 각 1회 계산한다. 두 Markdown/본문 JSON을 게시한다. 실패하면 정해진 실패 기록을 게시한다.

실제 수집·판정과 M3-04 두 보고서 로더·데모 운영은 이 구현 검증에서 실행하지 않았다.
