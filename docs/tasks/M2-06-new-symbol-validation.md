# M2-06 새 종목 사전 등록 V1 (S1-B 주 판정, S2-P 부 판정)

- 상태: 명세 작성(2026-10-28), Codex 검토 대기
- 구현: Codex / 검토: Claude Code
- 브랜치: `task/M2-06-new-symbol-validation`
- 근거: D97(이 작업의 결정), D93(검증 데이터 원칙), D95(S1-B·S2-P 정의), D96·PR #31(BTC·ETH 판정 INDETERMINATE), D88(위험 프로필·통과 기준), M2-04·M2-05 코드

## 목표

D96 판정(PR #31)에서 S1-B는 이익(+388.8 USDT), S2-P는 사실상 0(+2.26 USDT, 32거래)이었다. BTC·ETH의 2021-03 ~ 2026-10은 이제 모두 관측된 기간이다. 그래서 **아직 아무도 보지 않은 데이터인 새 종목 4개**에서, 전략 정의를 바꾸지 않고 한 번만 판정한다.

- **주 판정**: S1-B 단독(S2 끔). 데모 운영(M3-07) 진입 여부를 이것으로만 정한다.
- **부 판정**: S1-B × S2-P 조합(D96과 같은 격자). 통과해야 데모에서 S2-P를 켤 수 있다. 실패해도 주 판정에는 영향이 없다.

## 지켜야 할 원칙 (D93, D96, D97)

- **새 종목 가격 데이터는 사전 등록 전에 수집·조회·실행하지 않는다.** 종목 선정은 가격이 아닌 메타데이터(상품 정보·현재 24시간 거래대금)로만 한다.
- S1-B·S2-P의 규칙·격자·고정값은 D95·D96 그대로다. 결과를 본 뒤 하나라도 바꾸면 새 가설이며, 이 판정과 섞지 않는다.
- 두 판정(주·부)은 **같은 사전 등록, 같은 수집 데이터(같은 `data_hash`)** 로 한 번에 계산한다. 한쪽 결과를 보고 다른 쪽 조건을 바꾸지 않는다.
- 개발과 테스트는 합성 데이터로 한다.

## 범위

### 만들 것

1. **종목 선정 도구** (`tools/select_universe.py`)
   - Bybit 공개 API의 `instruments-info`(linear)와 `tickers`(linear)**만** 읽는다. kline·펀딩 이력은 읽지 않는다(테스트로 고정: 허용 엔드포인트 외 호출 시 실패).
   - 규칙(D97, 기계적으로 적용):
     1. `contractType = LinearPerpetual`, `quoteCoin = USDT`, `status = Trading`
     2. `launchTime < 2022-01-01T00:00Z`
     3. 제외: BTCUSDT·ETHUSDT, 기초 자산이 스테이블코인·법정화폐·금 연동인 것(USDC, USDE, FDUSD, DAI, TUSD, PAXG, XAUT 등 목록을 도구에 상수로 고정), 기초 자산 이름이 숫자로 시작하는 것(`1000…` 배수 계약)
     4. `turnover24h` 내림차순으로 정렬하고 상위 **4개**를 고른다. 같으면 심볼 이름순.
   - 출력: 선정 결과 JSON(규칙 버전, 응답 원본의 정규화 사본, `captured_at` UTC, 후보 전체 순위표, 선정 4개, `codec.digest`). 사람용 요약은 Markdown.
   - **한 번만 실행**하고, 결과를 이 작업 PR에 첨부한다. 선정 뒤에는 종목을 바꾸지 않는다. 데이터 문제의 처리는 8번 규칙을 따른다(교체 없음).

2. **종목 범위 일반화** (지금은 BTC·ETH 2개 고정)
   - `Symbol`에 선정된 4개를 추가한다(선정 결과 JSON과 같은 이름).
   - 2개 고정 가정을 걷어 낸다 (PR #32 Codex 검토로 목록 보완):
     - `BacktestRun`의 "BTCUSDT and ETHUSDT exactly once" 검사 → 설정된 종목 목록(정렬·중복 없음·1개 이상)
     - `backtest/walkforward.py`의 `tuple(Symbol)`, `campaign.py`·`portfolio/service.py`의 `for symbol in Symbol` → 설정된 종목
     - `statistics.py`의 계약별 분해(`("BTCUSDT", "ETHUSDT")`) → 실행 종목
     - `portfolio.invariants`는 주문 순회가 아니라 **전체 장부 정합성 검사**다. 범위를 설정 종목으로 줄이지 말고, 장부에 있는 모든 종목을 계속 검사한다(설정 밖 종목에 장부가 있으면 그 자체가 오류로 드러나야 함).
   - 연구 설정 `[backtest] symbols`로 종목 목록을 받고 manifest identity에 넣는다.
   - 데모·실거래 설정(`[bybit] symbols`)은 이번에 바꾸지 않는다. `config/__init__.py`의 `len(symbols) != 2 or set(symbols) != set(Symbol)` 검사는 enum이 늘면 기존 BTC·ETH 설정까지 거절하므로, **명시적 허용 집합 `{BTCUSDT, ETHUSDT}`** 과 비교하도록 바꾼다. 데모 종목은 Q26에서 정한다. enum이 늘어도 서비스가 설정 밖 종목을 순회하지 않음을 테스트로 고정한다.
   - **수집 차단**: `marketdata/ingest.py` CLI의 `--symbols` 선택지도 enum을 따라 늘어난다. BTC·ETH 외 종목 수집은 `--preregistration <사전 등록 JSON 경로>`를 요구하고, 파일의 `codec.digest`와 종목 목록을 확인한 뒤에만 시작한다. 사전 등록 전 실수로 새 종목 가격을 받는 일을 코드로 막는다.

3. **S2 끔 모드** (주 판정용)
   - 격자에 S1 후보만 있는 조합 `S1B`를 허용한다(S2 매개변수 없음). 실행기는 S2 신호를 만들지 않는다.
   - 위험 프로필은 D88 그대로 둔다(S1 배분 0.6, S2 배분 0.4는 쓰지 않고 비워 둠). 배분을 S1에 몰아주지 않는다.
   - 보고서는 S2 분해를 빈 값으로 둔다. 최소 정하기 거래 수는 S1만 검사한다.

4. **부 판정 통과 조건 추가**
   - `pass_criteria`에 전략별 최소 순손익을 선택 항목으로 추가한다: `min_strategy_net_pnl_usdt = { S2 = "0" }`. 부 판정은 D88 기준 + **확인 구간 합계 S2 순손익 > 0**이어야 PASS다.
   - 주 판정에는 이 항목을 넣지 않는다.

5. **기술용 기간 분해** (판정 기준 아님)
   - 보고서에 확인 구간 성과를 `2023-10-01` 앞뒤로 나눈 표를 추가한다. S1-B를 고를 때 BTC·ETH의 2023-10 이후 결과를 봤기 때문이다(D97 알려진 한계). 판정에는 쓰지 않는다.

6. **`v1:` 계약 확장** (PR #32 Codex 검토 P1·P2. 구현은 **M3-04**에서 설정 로더(M3-01 코드)와 트레이더를 함께 고친다. 이 작업은 연구 쪽 산출물만 만든다)
   - **설정 스키마**
     ```toml
     [strategy]
     report_path = "docs/reports/D97-primary.json"          # 주 판정(S1B) 보고서, 항상 필수
     # secondary_report_path = "docs/reports/D97-secondary.json"  # S2를 켤 때만 필수, 끌 때는 금지(이 예시는 S2 끔)

     [strategy.S1]                    # 항상 필수, enabled 필드 없음(S1은 끌 수 없음)
     candidate = "S1-B"
     source = "v1:<주 판정 본문 해시>"
     params = { entry_channel = 55, exit_channel = 20 }

     [strategy.S2]                    # S2 끔: enabled 하나만 허용
     enabled = false
     # S2 켬: enabled = true(또는 생략) + candidate·params·source = "v1:<부 판정 본문 해시>" 모두 필수
     ```
     - `enabled = false`이면 `candidate`·`params`·`source`가 있으면 **거절**(가짜 S2 값을 채우지 않음).
     - `enabled` 생략은 `true`로 본다(기존 설정 호환). 그때는 지금처럼 모든 필드가 필수다.
     - `source`는 전략마다 따로 둔다. S1 = 주 판정 해시, S2 = 부 판정 해시. 지금의 "S1·S2 source 같아야 함" 검사는 이 규칙으로 바뀐다.
     - `manual`은 개발용 그대로다(두 전략 모두 `manual`이거나, S2 끔 + S1 `manual`).
   - **검증 항목** (하나라도 아니면 시작 거부)
     1. 주 판정: `report_path` 본문 해시 재계산 = S1 `source`, 조합 `S1B`, 판정 **PASS**, S1 매개변수가 그 보고서의 COMPLETED 확인 구간 하나에서 실제로 선택된 값과 같음.
     2. S2를 켰을 때만, 부 판정: `secondary_report_path` 해시 = S2 `source`, 조합 `S1B-S2P`, 판정 **PASS**, 설정의 (S1, S2) 쌍이 부 보고서의 같은 COMPLETED 확인 구간에서 선택된 쌍과 같음.
     3. S2를 켰을 때 **두 보고서가 같은 판정에 묶였는지**: 사전 등록 id·sha256, `data_hash`, 종목 목록, 판정 구간이 모두 같음.
     4. 따라서 S2를 켜려면 S1 매개변수가 **주 판정의 선택값이면서 부 판정의 선택 쌍에도 들어 있어야** 한다. 그런 값이 없으면 S2는 켤 수 없다(S1 단독 운영).
   - 주 판정이 PASS가 아니면 부 판정 결과와 관계없이 운영 근거가 없다(D97).
   - D96처럼 조합 보고서 하나만 쓰던 이전 계약은 이 계약으로 대체한다(PASS한 이전 보고서가 없으므로 호환 대상 없음).

7. **2번 판정 실행 — 한 번 판정 절차** (D96 절차 그대로)
   - (a) **사전 등록 게시**: 구현·합성 검증·Claude 검토·병합 뒤, 코드 커밋, 선정 결과 JSON 해시, 두 판정의 설정 전체, 비용, 수집 범위, 알려진 한계를 담은 사전 등록 문서와 해시를 PR에 먼저 게시한다.
     - **계산량** (PR #32 Codex 검토): 실행기가 캠페인별 `per_run_seconds_12m`를 쓰므로 **4종목 합성 12개월 벤치마크를 두 모드(S1 단독, S1×S2)로 각각** 측정해 각 설정에 넣는다. 작업 수: 주 판정 학습 28 + 확인 ≤14, 부 판정 학습 224 + 확인 ≤14, 합계 ≤280회.
     - `max_compute_hours`는 캠페인별 **경과 시간 상한**이다: 남은 작업량 ÷ (workers × parallel_efficiency)에 여유를 더한다. 두 캠페인은 순차 실행이므로 사전 등록 문서에는 양쪽 합계 계획도 적는다.
     - 6종목 합성 실행은 일반화 테스트용이며 계산량 근거가 아니다.
   - (b) **수집과 고정(한 번)**: 4종목 일봉·1시간봉·펀딩, `[2022-01-01T00:00Z, 2026-10-01T00:00Z)`. 무결성 검사·스냅샷 고정만 하고 성과 계산은 하지 않는다.
   - (c) **최종 manifest 게시**: 두 판정 각각의 manifest를 계산 전에 PR에 게시한다. 두 manifest는 **같은 `data_hash`, 같은 사전 등록 id·sha256**을 가진다(두 격자의 최대 워밍업이 모두 S1-B (55,20)의 56일이라 같은 수집 범위·종목·상품/tier `captured_at`·수집 이력이면 같은 fingerprint가 나온다). 두 `prepare` 사이에 수집 이력·스냅샷을 바꾸지 않는다. 격자·기준은 각자 다르다.
   - (d) **판정 계산**: 주 판정 → 부 판정 순서로 각 1회. 중단되면 같은 manifest로만 재개한다.
   - 보고서 2개와 각 본문 JSON을 `docs/reports/`에 남긴다. 첫머리에 사전 등록 조건, 해시, D97 알려진 한계를 적는다.

8. **데이터 문제 처리 규칙** (PR #32 Codex 검토 P2. 결과를 보기 전에 고정)
   - **일시적 수집 오류**(네트워크·시간 초과·속도 제한): (b) 단계 안에서 같은 수집 범위·같은 종목으로 재시도·이어 받기를 한다. 성과 계산 전이므로 허용하고, 재시도 횟수와 시각을 수집 기록에 남긴다.
   - **회복 불가능한 입력 부족**(준비 단계 실패): 상품/tier 1단계 누락, 첫 펀딩 look-behind 누락, 워밍업 첫 봉 누락처럼 `campaign.prepare`가 예외로 멈추는 경우다.
     - 종목을 바꾸거나 기간을 줄이지 않는다.
     - **주·부 두 판정 모두 `INVALID_INPUT`** 으로 끝낸다. 계산은 하지 않는다.
     - 고정된 **실패 기록 JSON**(사전 등록 id·sha256, 수집 기록, 실패 종목·항목·예외 종류, 그때까지의 fingerprint, `codec.digest`)과 요약 보고서를 `docs/reports/`에 남긴다. 다시 하려면 새 결정·새 사전 등록이 필요하다.
   - **판정 구간 안의 봉 공백**: 지금 규칙 그대로 해당 확인 구간을 `INVALID_DATA`로 두고 무효 비율(14개 중 3개 이하)에 넣는다. 주·부는 같은 데이터를 쓰므로 같은 구간이 무효가 된다.
   - 합성 회귀로 세 경우(재시도 뒤 같은 fingerprint, 준비 실패 → 두 판정 `INVALID_INPUT` 기록, 구간 공백 → 두 판정의 같은 구간 `INVALID_DATA`)를 고정한다.

| 항목 | 값 |
|---|---|
| 종목 | 1번 규칙으로 고른 4개 |

| 통과(부) | 주와 같은 기준 + 확인 구간 S2 순손익 > 0 |
