## 범위

### 만들 것 (`app.py`, `live/`, `health/`)

1. **시작 순서** (03 4.3절 1~11단계 그대로)
   - 설정·비밀 → Oracle·마이그레이션 버전 → 정지 상태 복원 → 개인 WS 선구독·버퍼 → REST 스냅샷 → 반영·재생 → 보호 확인 → 안정화 확인 → 시세 WS → 정지(sync) 해제.
   - `ai.mode=disabled` 고정(M3). 시작 시 환경·AI 모드·설정 해시·전략 후보를 텔레그램으로 알림(M3-05).

2. **전략 설정** (PR #15 검토 4번)
   - M2-02 전략은 매개변수 기본값이 없다. M3-01 설정 로더가 `[strategy.S1]`·`[strategy.S2]`를 **필수**로 읽는다: 후보 식별자(S1-A/S1-B, S2-A/S2-B, 재설계 S2-P — D95), 그 후보의 모든 필수 매개변수, `source`.
   - `source` 형식 (D94, PR #26 검토 P1):
     - `v1:<보고서 본문 해시>` — 사전 등록 V1 캠페인 보고서에서 고른 값. **검증 계약** (PR #26 재검토 P2):
       - **기계 판독 원본**: 캠페인은 Markdown 보고서와 함께 **보고서 본문 JSON**(지금 결과 폴더의 `report-data.json`과 같은 내용, 기존 `backtest.codec` 정규화)을 `docs/reports/<보고서 이름>.json`으로 발행한다. Markdown은 사람이 읽는 사본이고 검증에 쓰지 않는다.
       - **해시**: `<보고서 본문 해시>` = 그 JSON 본문의 `codec.digest`(Markdown에 적힌 'Research body SHA-256'과 같은 값). 로더는 파일을 읽어 **해시를 다시 계산**해 비교한다(문자열 검색 금지).
       - **경로**: 설정 `[strategy] report_path`로 받고, 설정 파일 위치 기준 상대 경로로 푼다(03 3.1절, cwd·소스 트리에 의존하지 않음).
       - **연결**: 본문에 캠페인 manifest 해시와 사전 등록 식별자(D96 등)가 들어 있어야 한다.
       - **확인 항목**: (1) 해시 일치, (2) 고른 조합의 V1 판정 PASS, (3) 설정의 **S1×S2 매개변수 쌍**이 그 보고서의 **같은 확인 구간에서 실제로 선택된 쌍**과 정확히 같음(서로 다른 구간의 S1과 S2를 섞은 쌍은 거부). 하나라도 아니면 시작 거부.
     - `manual` — 개발·연결 확인용. 운영 승인이 아니다.
     - 예전 형식 `m2-04:…`는 받지 않는다(첫 보고서는 FAIL).
   - 누락·범위 밖·후보와 맞지 않는 매개변수·알 수 없는 후보면 시작 거부(M2-02의 매개변수 검사 재사용). 전략 설정은 설정 해시에 포함되고 `config_versions`에 남는다.
   - **M3-07 데모 1주 운영은 `source = v1:…`(PASS 확인됨)일 때만 완료 판정에 넣는다.** M3-01·03·04 개발과 24시간 연결 시험은 `manual`로 해도 되지만, 그 기간은 운영 판정에 들어가지 않는다. 이로써 05의 M2 → M3 순서를 지킨다.

3. **경계 처리** (D76 순서, PR #15 검토 3번)
   - 확정 봉 하나가 올 때마다 바로 처리하지 않는다. **경계 T마다 필요한 입력을 모은 뒤 한 번만 처리**한다.
   - T의 필수 입력: 두 계약의 1시간봉(시작 T−1h, `confirm=true`). T가 UTC 00:00이면 두 계약의 일봉(시작 T−1d)도.
   - 수집 장벽: 필수 입력이 다 모이면 처리 시작. 대기 기한(설정, 예: 90초)이 지나면 빠진 봉을 REST(M2-01 클라이언트)로 받는다. 그래도 없으면 그 계약은 이번 T에 **신호를 만들지 않고**(MarketDataGuard가 진입 정지) 알림. 다른 계약은 진행. 손절·청산은 영향 없음.
   - 같은 봉이 다시 오면 무시(멱등). 이미 끝난 T의 봉은 무시. 다음 T 봉이 먼저 와도 현재 T가 끝날 때까지 버퍼에 둔다.
   - 처리 순서(T 하나): ① 체결·손절 반영 확인 — 개인 WS 이벤트를 큐에서 모두 반영하고, REST 체결 조회(마지막 확인 시각 이후)로 빠진 체결이 없는지 확인 → ② 펀딩 반영(아래) → ③ T가 00:00이면 계좌 스냅샷으로 `start_day`(D72·D85), 일일 정지 해제, 곧바로 위험 재검사 → ④ 신호 S1(00:00만) → S2, 각각 BTC → ETH → ⑤ 위험 게이트(M1-03) → ⑥ 주문 전송기(M1-06: SUBMITTED 커밋 후 잠금 밖에서 전송).
   - **펀딩** (PR #15 재검토 1번): 계좌 펀딩은 공개 펀딩율이 아니라 계좌 기록(체결 내역의 펀딩 유형 또는 transaction-log)으로 반영한다(D87 실제 정산 시각).
     - **정산 시각 보유량으로 배분**: ①단계에서 경계 T 기준 전략별 보유량 스냅샷 `position_snapshots(T, 전략, 계약, 수량)`을 남긴다. 값은 "체결 시각이 T보다 이른 체결까지 반영한 수량"이다(이미 반영된 T 이후 체결은 빼서 계산). 귀속 보류·미반영 체결 중 T 이전 것이 있으면 ①단계는 끝나지 않는다. Bybit 펀딩 정산 시각은 정시이므로 시간 경계 스냅샷으로 모든 정산 시각을 덮는다.
     - 펀딩 기록이 언제 도착하든 **정산 시각의 스냅샷**으로 전략별로 나눈다. 그 사이 청산·진입이 있어도 비용이 다른 전략으로 가지 않는다. 스냅샷이 모두 0인데 비용이 0이 아니면 예외로 멈추지 않고 "미배분 펀딩"으로 계좌에만 기록·알림한다.
     - **선행 변경(M1-04)**: `funding(id, symbol, amount)`를 `funding(id, symbol, amount, settled_at)`으로 바꾸고 현재 장부 대신 `position_snapshots`로 배분한다. 이 변경은 M3-04 안에서 하되 M1-04 테스트를 함께 고친다(Codex 판단으로 별도 작은 PR로 먼저 해도 됨).
     - **거래일 귀속**: 펀딩 손익은 정산 시각이 속한 거래일(D81)에 넣는다. 자정 정산은 전날 몫이다.
     - **자정 회계 경계**: T가 00:00이고 그 시각 스냅샷에 보유가 있는 계약이 있으면, ③단계(`start_day`)는 그 계약들의 00:00 펀딩 기록을 받을 때까지 기다린다. 기다리는 동안 모든 계약의 **신규 진입은 보류**하고(일일 기준이 없으므로), 손절·청산·보호는 계속한다. 대기 기한을 넘기면 REST로 조회하고, 그래도 없으면 알림을 반복하며 계속 보류한다. 기록을 받은 **뒤에** `start_day`용 계좌 스냅샷을 찍는다. 스냅샷 시각이 transaction-log의 정산 시각보다 이르면 다시 찍는다. 그래서 자정 펀딩은 항상 스냅샷에 들어 있고(전날 손익), `start_day`를 나중에 고치지 않는다.
     - 자정 외 정산 시각의 늦은 펀딩은 신호 처리를 막지 않는다(배분은 스냅샷 기준이라 늦어도 결과가 같다).
   - **단계 기록과 복원** (PR #15 재검토 2번): 각 단계는 **상태 변경·그 단계의 출력·체크포인트를 같은 UoW로 커밋**한다. 커밋 전에 죽으면 그 단계 전체가 없던 일이 되고, 커밋 뒤에 죽으면 저장된 출력으로 다음 단계를 잇는다.

     | 단계 | 같은 UoW에 커밋하는 것 | 재시작 시 |
     |---|---|---|
     | 경계 입력 | `boundary_inputs(T, 계약, 주기, OHLCV)` — 장벽을 통과한 확정 봉(REST 보충 포함) | 저장된 입력을 쓴다. 다시 받지 않는다 |
     | ① 체결 확인 | `position_snapshots(T, …)` + 체크포인트 | 저장된 스냅샷 사용 |
     | ② 펀딩 | 펀딩 반영(펀딩 ID 멱등) + 체크포인트 | 반영된 ID는 건너뜀 |
     | ③-1 자정 준비 | (펀딩 대기·확인이 끝난 뒤) `start_day`에 쓸 계좌 스냅샷(시각·지갑 잔고·미실현 손익)과 그 스냅샷에 들어간 입출금 참조를 **불변 준비 레코드**(`boundary_inputs`, 종류 ACCOUNT_SNAPSHOT)로 먼저 커밋 | 준비 레코드가 있으면 그것을 쓰고 **다시 찍지 않는다**. 없으면 아직 아무것도 쓰지 않은 상태이므로 새로 찍는다. 준비 커밋이 결과 불명이면 M3-02의 `txn_id` 판정을 거친다 |
     | ③-2 자정 반영 | 준비 레코드를 읽어 `start_day`·일일 정지 해제·위험 재검사 결과 + 체크포인트 | 같은 준비 레코드로 다시 계산. 더 늦은 평가액으로 다시 잡지 않는다 |
     | ④ 신호 | `boundary_outputs(T, 전략, 계약)` — 신호 목록(진입 예상가·손절가 포함), 추세 상태·추적 손절 + 체크포인트 | 저장된 신호를 쓴다. 다시 계산하지 않는다 |
     | ⑤ 위험 게이트 | 신호마다 결정·주문(M1-03의 한 UoW, signal_id 유일). 결정에 **실제로 쓴 위험 기준**(평가액, 정지 상태, 보유·예약, 시세 신선도 판단)을 함께 저장 | 결정이 있는 신호는 그대로 복원. 결정이 없는 신호는 지금처럼 잠금을 얻은 뒤 **최신** 평가액·정지 상태·보유·예약·시세 신선도로 판단한다(과거 평가액으로 고정하지 않음, PR #15 재검토) |
     | ⑥ 전송 | 체크포인트로 판단하지 않는다 | M1-06의 SUBMITTED·저널·UNKNOWN 복구 규칙을 그대로 따른다 |

     - T가 너무 오래됐으면(설정, 예: 2시간) ④~⑤를 건너뛰고 기록만 남긴다. ①~③은 회계라서 건너뛰지 않는다.
     - 이 테이블들은 M3-02 스키마에 넣는다.
   - 이 경계 처리 함수는 M2-03 백테스트 실행기와 **같은 함수**를 쓴다(입력 수집 방식만 다름).

4. **정기 작업**
   - 1분마다 REST 정기 대조(03 4.2절), 미반영 체결·귀속 보류·UNKNOWN 해소 판단 실행(M1-02).
   - M1-04 outbox 처리: `actions()`를 읽어 저널 인수 → 전송·취소·조회 → acknowledge. 전체 손절 조회가 성공했을 때만 `confirm_stop_snapshot`(조회 **시작** 시각). 계좌 동기화가 끝나면 `recover_system_pause` 시도.
   - 하루 1회 상품·위험 단계 갱신(D79), 수수료 확인 기록.
   - **지정가 진입 만료 취소**(M2-05 3번, D95): 동기화기 `tick`에서 `expires_at`이 지난 미종결 진입의 잔량을 저널·취소 경로로 취소한다. 불명 응답은 UNKNOWN 규칙, 재시작 시 진입을 열기 전에 처리, 부분 체결 보유는 유지(CloseIntent 아님). 데모에서 S2-P를 켜기 전 필수.
   - 진입 체결 직후 거래소가 알려 준 **실제 강제청산가**로 02 3.1절 부등식을 다시 확인(D62). 만족하지 않으면 알림 후 그 수량을 줄인다.

5. **상태 확인 주소** (`health/`)
   - `127.0.0.1`의 HTTP 주소 하나: 프로세스 살아 있음, 마지막 처리한 경계 T, 개인 WS 연결 상태, 마지막 Oracle 커밋 시각, 정지 상태 요약. Watchdog(M3-06)만 읽는다. 외부 노출 금지.

6. **종료**: 신호를 받으면 신규 진입을 멈추고 진행 중인 커밋을 마친 뒤 종료. 손절은 거래소에 남아 있으므로 청산하지 않는다(P1).

  - 자정 봉 4개(BTC·ETH × 1시간·일봉)의 **도착 순서 순열 전부** → 처리 결과·주문이 같고 S1 → S2, BTC → ETH 순서
  - 한 계약 봉이 대기 기한을 넘김 → REST 보충 성공 / 실패 시 그 계약만 신호 없음·알림
  - 같은 봉 재전달, 다음 T 봉 먼저 도착
  - 단계마다 두 가지 장애를 따로: (a) 상태·출력 변경 뒤 **커밋 전** 종료, (b) **커밋 성공 뒤** 다음 단계 전 종료. **외부 입력 이력(체결·입출금·시세·정지 명령)이 같을 때** `start_day`·신호·결정·주문이 중단 없는 실행과 같고 주문 중복 없음
  - ③: 준비 레코드 커밋 전 종료 → 새 스냅샷으로 진행 / 준비 레코드 커밋 뒤 종료 → 같은 스냅샷 재사용(평가액이 그 사이 바뀌어도 `start_day`는 같음) / ③-2 커밋 전 종료 → 같은 준비 레코드로 재계산 / 준비 커밋 결과 불명 → `txn_id` 판정 뒤 위 둘 중 하나

## M2-02 연결 보완 (PR #22 검토, 2026-10-23)

- Wilder RSI·ATR은 마지막 10×n개 봉에서 seed부터 계산한다. `strategy.candidates.required_bars(params)`가 직전 지표까지 포함한 최소 평가 창을 반환한다. 운영 시작 시 최소 그 수의 마감 봉을 적재하며, 백테스트는 한 번 검증한 전체 이력에서 `through(start, lookback=required_bars(params))`로 잘라 평가한다. 이력 전체 접두를 매번 만들지 않는다.
- S1 결과가 EXIT면 청산 라우터로 전달하고 그 봉에서는 `trail_stop`을 호출하지 않는다. 목표 후보가 종가를 이미 넘어선 경우 기존 목표를 유지하며 ENTRY를 내지 않는 규칙이다. 최초 판단에 직전 목표가 없으면 S1State.stop_price는 None일 수 있다. 추세 자체는 유지하며 다음 유효한 판단에서 목표와 ENTRY가 만들어진다.
