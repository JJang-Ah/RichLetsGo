## 범위

### 만들 것 (`app.py`, `live/`, `health/`)

1. **시작 순서** (03 4.3절 1~11단계 그대로)
   - 설정·비밀 → Oracle·마이그레이션 버전 → 정지 상태 복원 → 개인 WS 선구독·버퍼 → REST 스냅샷 → 반영·재생 → 보호 확인 → 안정화 확인 → 시세 WS → 정지(sync) 해제.
   - `ai.mode=disabled` 고정(M3). 시작 시 환경·AI 모드·설정 해시·전략 후보를 텔레그램으로 알림(M3-05).

2. **전략 설정** (PR #15 검토 4번)
   - M2-02 전략은 매개변수 기본값이 없다. M3-01 설정 로더가 `[strategy.S1]`·`[strategy.S2]`를 **필수**로 읽는다: 후보 식별자(S1-A/S1-B, S2-A/S2-B), 그 후보의 모든 필수 매개변수, `source`.
   - `source`는 `m2-04:<보고서 파일 해시>`(사용자가 M2-04 보고서를 보고 고른 값) 또는 `manual`(개발·연결 확인용).
   - 누락·범위 밖·후보와 맞지 않는 매개변수·알 수 없는 후보면 시작 거부(M2-02의 매개변수 검사 재사용). 전략 설정은 설정 해시에 포함되고 `config_versions`에 남는다.
   - **M3-07 데모 1주 운영은 `source = m2-04:…`일 때만 완료 판정에 넣는다.** M3-04 개발·24시간 시험은 `manual`로 해도 된다. 이로써 05의 M2 → M3 순서를 지킨다.

3. **경계 처리** (D76 순서, PR #15 검토 3번)
   - 확정 봉 하나가 올 때마다 바로 처리하지 않는다. **경계 T마다 필요한 입력을 모은 뒤 한 번만 처리**한다.
   - T의 필수 입력: 두 계약의 1시간봉(시작 T−1h, `confirm=true`). T가 UTC 00:00이면 두 계약의 일봉(시작 T−1d)도.
   - 수집 장벽: 필수 입력이 다 모이면 처리 시작. 대기 기한(설정, 예: 90초)이 지나면 빠진 봉을 REST(M2-01 클라이언트)로 받는다. 그래도 없으면 그 계약은 이번 T에 **신호를 만들지 않고**(MarketDataGuard가 진입 정지) 알림. 다른 계약은 진행. 손절·청산은 영향 없음.
   - 같은 봉이 다시 오면 무시(멱등). 이미 끝난 T의 봉은 무시. 다음 T 봉이 먼저 와도 현재 T가 끝날 때까지 버퍼에 둔다.
   - 처리 순서(T 하나): ① 체결·손절 반영 확인 — 개인 WS 이벤트를 큐에서 모두 반영하고, REST 체결 조회(마지막 확인 시각 이후)로 빠진 체결이 없는지 확인 → ② 펀딩 반영(아래) → ③ T가 00:00이면 계좌 스냅샷으로 `start_day`(D72·D85), 일일 정지 해제, 곧바로 위험 재검사 → ④ 신호 S1(00:00만) → S2, 각각 BTC → ETH → ⑤ 위험 게이트(M1-03) → ⑥ 주문 전송기(M1-06: SUBMITTED 커밋 후 잠금 밖에서 전송).
   - **펀딩**: 계좌 펀딩은 공개 펀딩율이 아니라 계좌 기록(체결 내역의 펀딩 유형 또는 transaction-log)으로 반영한다(M1-04 `funding(id, symbol, amount)`, D87 실제 기록 시각). T가 계약의 펀딩 시각이고 그 계약 포지션이 있었으면 펀딩 기록을 대기 기한까지 기다리고, 없으면 REST로 조회. 그래도 없으면 알림하고 진행하며, 나중에 도착하면 그때 반영한다(펀딩 ID 멱등). `start_day`는 계좌 스냅샷 기준이므로 늦은 펀딩 반영과 이중 계산되지 않는다.
   - **체크포인트**: T의 단계(①~⑥) 완료를 Oracle `boundary_checkpoints(T, 단계)`에 남긴다. 재시작하면 마지막 완료 단계 다음부터 이어 간다. T가 너무 오래됐으면(설정, 예: 2시간) 신호 단계(④~⑥)는 건너뛰고 기록만 남긴다.
   - 이 경계 처리 함수는 M2-03 백테스트 실행기와 **같은 함수**를 쓴다(입력 수집 방식만 다름).

4. **정기 작업**
   - 1분마다 REST 정기 대조(03 4.2절), 미반영 체결·귀속 보류·UNKNOWN 해소 판단 실행(M1-02).
   - M1-04 outbox 처리: `actions()`를 읽어 저널 인수 → 전송·취소·조회 → acknowledge. 전체 손절 조회가 성공했을 때만 `confirm_stop_snapshot`(조회 **시작** 시각). 계좌 동기화가 끝나면 `recover_system_pause` 시도.
   - 하루 1회 상품·위험 단계 갱신(D79), 수수료 확인 기록.
   - 진입 체결 직후 거래소가 알려 준 **실제 강제청산가**로 02 3.1절 부등식을 다시 확인(D62). 만족하지 않으면 알림 후 그 수량을 줄인다.

5. **상태 확인 주소** (`health/`)
   - `127.0.0.1`의 HTTP 주소 하나: 프로세스 살아 있음, 마지막 처리한 경계 T, 개인 WS 연결 상태, 마지막 Oracle 커밋 시각, 정지 상태 요약. Watchdog(M3-06)만 읽는다. 외부 노출 금지.

6. **종료**: 신호를 받으면 신규 진입을 멈추고 진행 중인 커밋을 마친 뒤 종료. 손절은 거래소에 남아 있으므로 청산하지 않는다(P1).

### 만들지 않을 것

- AI 호출(M4), 그림자 장부 운영(M4), 대시보드(M5)

## 완료 조건

- [ ] 가상 거래소(M1-05)와 가짜 시계로 실행 루프를 돌리는 통합 테스트:
  - 자정 봉 4개(BTC·ETH × 1시간·일봉)의 **도착 순서 순열 전부** → 처리 결과·주문이 같고 S1 → S2, BTC → ETH 순서
  - 한 계약 봉이 대기 기한을 넘김 → REST 보충 성공 / 실패 시 그 계약만 신호 없음·알림
  - 같은 봉 재전달, 다음 T 봉 먼저 도착
  - 경계 처리 중 단계마다 재시작 → 체크포인트 다음부터, 주문 중복 없음
  - 펀딩 기록 지연 → 알림 후 진행, 늦게 도착하면 한 번만 반영
- [ ] 전략 설정: 누락·범위 밖·알 수 없는 후보 → 시작 거부. `source`가 설정 해시에 포함.
- [ ] 시작 순서 테스트: 각 단계 실패 시 진입이 열리지 않음
- [ ] 실제 강제청산가가 근사와 달라 부등식을 깨면 알림·축소
- [ ] health 주소가 `127.0.0.1`에만 열리고 비밀 정보를 내지 않음
- [ ] (수동) 데모에서 24시간 연속 실행, 자정 경계 1회 통과 기록
