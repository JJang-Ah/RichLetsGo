## 목표

D97까지 S2 계열은 세 번 연속 우위가 없었다. D98은 S2를 "지금 거래대금이 몰리고 돌파하는 종목을 고르는" S2-M으로 바꾸고, 운영 구조(M1/M3)를 고치기 전에 **설계용 풀에서 신호 자체에 우위가 있는지만 가볍게 확인**한다. 이 작업의 결과는 04 3.3 4의 진행 기준(go/no-go) 하나다.

- 통과: 2단계(04 3.3 5) 설계를 시작한다. 판정용 풀은 여전히 손대지 않는다.
- 실패: S2-M을 버린다. 판정용 풀은 미관측 상태로 남는다.
- 어느 쪽이든 이 결과는 설계 참고이지 판정이 아니다.

## 지켜야 할 원칙 (데이터 접근 순서, D93·D98)

1. **풀 목록 게시 전**: 어떤 새 종목의 가격·펀딩도 받지 않는다. 07a 도구는 `instruments-info`만 읽는다.
2. **풀 목록 병합 후**: 설계용 풀의 가격·펀딩만 받는다. 판정용 풀 심볼은 수집 도구가 **네트워크 호출 전에** 거절한다.
3. **판정용 풀 가격은 2단계 사전 등록 전까지 수집·조회하지 않는다.** 이 작업의 어떤 도구도 판정용 풀 심볼로 kline·펀딩을 요청할 수 없어야 한다(테스트로 고정).
4. 연구 조건(격자·고정값·Q30 수치·비용·진행 기준)은 **연구 사전 등록**으로 먼저 게시하고, 연구는 한 번만 실행한다. 결과를 본 뒤 하나라도 바꾸면 새 가설이다.
5. 개발·테스트는 합성 데이터로 한다. 실데이터 실행은 각 부분의 "수동, 한 번" 단계뿐이다.

## 07b 설계용 풀 수집과 감사 (04 3.3 1·3·4의 데이터 부분)

### 만들 것

- `research/d98/collect.py`, `research/d98/store.py`, `research/d98/audit.py`, `tools/d98_collect.py`, `tools/d98_audit.py`.
- **입력**: `--pool docs/reports/D98-pool.json`. 시작할 때 파일 digest를 다시 계산해 본문과 맞는지 확인한다. 수집 대상은 그 파일의 **설계용 풀 계약**뿐이다. 판정용 계약이나 목록에 없는 심볼을 지정하면 **네트워크 호출 전에** 거절한다.
- **허용 엔드포인트**: `GET /v5/market/kline`(`interval=60`, BTC 기준 입력만 `interval=D`), `GET /v5/market/funding/history`. 요청 심볼이 설계용 목록에 없으면 전송 래퍼에서도 거절(이중 차단).
- **범위** (봉과 정산의 경계는 따로 정한다. 수집 시작 `S = max(floor_hour(launch), 2021-11-01T00:00Z)`, 끝 `T = 2026-10-09T00:00Z`, 폐지 `D`)
  - **1시간봉**: 시작 `s`가 `S ≤ s`이고 **끝 `s + 1h ≤ min(T, D)`인 완결 봉만**. 정시가 아닌 `D`의 미완결 봉은 받지도, `L_a` 후보로 쓰지도 않는다.
  - **펀딩 정산**: 시각 τ가 `S − 24h ≤ τ < T`이고 폐지 계약이면 **`τ ≤ D`(D 포함)**. 폐지 청산의 `τ = E_a` 정산(`E_a = D`인 경우 포함)이 수집·저장·연구·`data_hash`에 같은 규칙으로 들어간다. 앞쪽 24시간은 첫 연구 시각의 τ₁·τ₂·τ₃ 확보용 여유다.
  - 이 구간이 비면 수집하지 않고 사유를 남긴다.
  - BTCUSDT 일봉(기준 입력): `[2020-11-07T00:00Z, 2026-10-09T00:00Z)`.
- **저장**: 별도 SQLite 파일(`--db`, 기본은 설정의 백테스트 데이터 경로 아래 `d98-design.sqlite`). 테이블 `bars_1h(symbol, start, open, high, low, close, volume, turnover)`, `btc_daily(start, …)`, `funding(symbol, time, rate)`, `collection_log`. 같은 키를 다른 값으로 다시 쓰면 오류(기존 store와 같은 원칙). 이어 받기를 지원한다.
- 위 범위 밖에서 돌아온 봉·정산(예: 상장 전 봉, 폐지 뒤 정산)은 저장은 하되 연구·`data_hash`에서 쓰지 않고 감사에 개수를 적는다. "범위 안"의 판정은 수집·감사·해시·연구가 **같은 함수 하나**를 쓴다.
- **재시도**: `RetryPolicy` 그대로. 재시도 횟수·시각을 `collection_log`에 남긴다.
- **규모 예상**(검토용): 설계용 계약 약 500~600개 × 최대 약 43,000개 1시간봉 ≈ 최대 2,600만 행. kline 1,000개/요청 기준 약 2만~3만 요청이다. 실제 요청 속도는 Bybit 공개 한도 안에서 설정값으로 둔다.
- **메모리**: 수집·감사·해시·연구 모두 **계약 단위로 읽고 처리**한다. 전체 DB를 한 객체로 메모리에 올리지 않는다. 병렬 worker 수는 설정값으로 제한한다.
- **합성 벤치마크**(07b·07c 각 PR): 600계약 × 43,000봉 규모 합성 DB로 저장·감사·해시·연구의 **경과 시간과 최대 메모리**를 측정하고, 1 worker와 다중 worker의 출력 digest가 같음을 확인한다.

### 감사 (가격 결과를 계산하지 않음)

`tools/d98_audit.py`가 저장된 데이터에서 아래를 계산해 `docs/reports/D98-collection-audit.json`(요약 `.md`)으로 낸다. **수익·신호·지표 값은 계산하지 않는다.** 봉과 정산의 존재 여부와 시각만 본다.

- 계약별: 수집 구간, 기대/실제 1시간봉 수, 누락 구간 목록, `F`(첫 봉), `L_a`, `E_a`, `L_e`, 폐지 꼬리 분류(허용 ≤ 24h / 초과 / 해당 없음), 데이터 끝, 펀딩 기록 수, 관측된 정산 간격 분포, Trading 계약의 `fundingInterval`과 최근 간격 불일치(기술용).
- BTC 일봉 완결성. 하나라도 빠지면 감사 결과 `BTC_INCOMPLETE`, 연구 진행 불가.
- **입력 부족률**(04 3.3 4): 평가 기회 → 메타데이터 자격 → 과거 입력 완결성 단계까지만 센다. 이 단계는 조합과 무관하고 가격 값을 쓰지 않는다. 5%를 넘으면 감사 결과 `STUDY_UNDECIDABLE`.
- `data_hash` (스트리밍, 형식 고정): `codec.digest`에 DB 전체를 넘기지 않는다.
  1. 계약별 해시: 범위 안 1시간봉을 시작 시각 순으로, 행마다 `codec.encode([start_ms, open, high, low, close, volume, turnover]) + "\n"`을 UTF-8로 sha256에 순차 투입 → `bars_sha256`. 정산도 같은 방식(`[time_ms, rate]`) → `funding_sha256`.
  2. BTC 일봉도 같은 방식 → `btc_daily_sha256`.
  3. **해시 manifest**: `{"version": "D98-data-v1", "contracts": [[symbol, bars_sha256, funding_sha256, 봉 수, 정산 수], …(심볼 이름순)], "btc_daily": [btc_daily_sha256, 봉 수]}`. `data_hash = codec.digest(manifest)`.
  - manifest 전체를 감사 JSON에 넣는다(계약 단위로 어디가 달라졌는지 추적 가능). 연구 도구는 같은 함수로 다시 계산해 확인한다.

#### 실행 코드 고정 (등록 커밋과 실행 checkout 분리)

등록 문서를 병합하면 저장소 HEAD는 등록 커밋 C가 아니라 문서 커밋 P가 된다. 그래서 다음 방식으로 고정한다.

- 등록 파일·감사·풀 파일은 병합된 main(P 이후)에서 읽은 것을 **외부 경로 인자**(`--preregistration`, `--audit`, `--pool`)로 넘긴다. DB는 `--db`.

- 출력 디렉터리 `backtest_results/d98-study/<등록 digest>/`에 **원자적 잠금 파일**(`O_CREAT | O_EXCL`)을 만들고 상태 `RUNNING`을 기록한 뒤에만 계산을 시작한다. 이미 잠금이 있으면 동시 실행으로 보고 거절한다.
