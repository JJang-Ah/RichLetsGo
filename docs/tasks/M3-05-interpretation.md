## 구현 해석

### I1. Bot API·저장 위치·수신 소유권

HTTPS `getUpdates` 롱 폴링만 사용한다. 토큰은 Windows 자격 증명 관리자에서 메모리로만 받고 URL·예외·HTTP 추적·DB·로그·테스트 산출물에 남기지 않는다. 리다이렉트를 허용하지 않는다. 실 봇의 webhook을 자동 삭제하거나 대기 업데이트를 버리는 API를 호출하지 않는다. webhook 충돌/다른 poller 충돌은 텔레그램 장애로 알리고 명령 수신을 보류한다.

환경·계좌 DB의 기존 recovery 저장 API에 `telegram_inbox:`·`telegram_cursor:`·`telegram_outbox:` 접두어로 수신/커서/발송 상태를 저장하는 안이다. 발송 이력은 `alerts`에도 같은 UoW로 투영한다. 스키마 변경 필요 여부는 구현 전에 확인하고 기존 V001/V002를 수정하지 않는다. bot_id는 `getMe`의 공개 숫자 ID로 식별하며 토큰/토큰 해시는 식별자로 저장하지 않는다. 한 봇은 한 환경·계좌의 poller만 소유하도록 운영 계약에 명시한다. 환경/계좌/봇 교체 시 다른 커서를 재사용하지 않는다.

### I2. 수신 커밋과 update_id 재처리 방지

받은 배치의 필요한 필드만 inbox에 저장하고 다음 offset을 **같은 UoW로 확정한 뒤** 그 offset으로 다음 `getUpdates`를 요청한다. 원문 메시지 전체를 보관하지 않고 명령 allowlist·필요한 대상·요청자·채팅·업데이트/콜백 식별자만 검증해 남긴다. 알 수 없는 업데이트는 버린 이유만 기록한다. 수신 저장 실패/커밋 불명 때는 원격 확인 offset을 전진시키지 않고 기존 DB 커밋 판정을 따른다. Telegram 서버가 보관하는 최대 24시간을 넘어선 누락은 복구 가능하다고 표시하지 않는다.

inbox 처리 상태와 공통 서비스의 영속 명령 결과를 대조해 재개한다. Telegram 콜백 업데이트 자체의 중복 제거와 **원래 명령의 request_id**를 구분한다. 콜백에서 새 명령 ID를 만들지 않고 기존 `TelegramCommands`와 V002 출처별 멱등 매핑을 재사용한다. `confirming`·일시적 `unavailable`을 실행 완료로 오인하지 않는다. 커밋 결과 판정 전에는 새 ID로 명령을 재실행하지 않는다. 확정된 도메인 결과와 응답 outbox 생성 사이에 중단돼도 저장 결과로 응답을 복원한다.

재시작으로 기존 확인 번호는 무효다. 재생한 과거 `/resume`·`/cancel`·`/resolve`가 새로운 유효 확인 번호를 자동 발급하거나 실행되게 하지 않는다. 이미 확정된 명령은 기존 결과만 반환하고, 미확정 확인 요청은 중단 기록 후 새 사용자 요청을 요구한다. accepted 취소는 공통 서비스의 고정 대상 outbox만 계속 추적한다. 장기간 무수신 후 update_id 재선정은 Q4에서 별도로 고정한다.

### I3. 공통 CommandService의 재사용 범위

Telegram은 파싱·메시지 표시·콜백 연결만 맡는다. `/pause`·`/resume`·`/cancel`·`/resolve`의 권한·확인·계좌 잠금·의도/결과 기록·커밋 불명 판정·대상 고정·재시도·재개 위험 검사는 기존 `CommandService`/`ResumeService`를 호출한다. `CommandService.tick()`은 기존 Trader maintenance 배선을 유지하며 폴링 성공 여부에 종속시키지 않는다. 웹과 다른 정지 해제나 주문 전송 경로를 만들지 않는다.

현행 서비스의 변경 명령 집합에는 `/status`가 없고 미등록 사용자 거절은 감사 저장 전 발생한다. 공통 서비스에 권한 검사/거절 감사와 읽기 전용 상태 조회 진입점을 보완한다. 읽기 조회가 변경 명령/취소 outbox를 만들지 않도록 분리하되 `authorize_command`는 모든 명령에서 실행한다. 미등록 사용자는 한 업데이트당 한 거절 감사만 남기고 메시지/확인 버튼을 보내지 않는다. 감사 저장 장애도 텔레그램 작업에서 재시도하며 권한을 우회하지 않는다.

`/status`는 일관된 내부 스냅샷에서 D81 손익·포지션/손절·한도·정지·마지막 확정 봉/체결·키 잔여일을 포맷한다. 없는 값은 미확인으로 표시한다. 상태 조회 중 계좌 잠금을 잡고 외부 API를 기다리지 않는다. `telegram.allowed_user_ids`와 `control.allowed_ids`의 Telegram 주체가 불일치하면 시작 설정 오류로 거절하는 안이며, 두 목록을 합집합으로 넓히지 않는다.

### I4. 인라인 확인의 만료·소유권·일회성

M5-01b와 같은 **60초**를 사용한다. Bot API의 64바이트 제한 안에서 추측 불가능한 opaque nonce만 callback_data에 담고 서버가 원래 명령 문맥을 찾는다. 확인 소유자는 `from.id`, 채팅, 봇, 환경·계좌, 출처, 원래 request_id와 묶고 확인 메시지 ID도 검증한다. message가 없거나 확인 대상 메시지를 검증할 수 없으면 실행하지 않는다. payload의 명령/대상/요청자 주장을 신뢰하지 않는다.

만료·다른 사용자·다른 채팅·재시작 전 번호·재사용은 공통 서비스 검사와 어댑터 바인딩 검사에서 거절한다. 버튼 중복 클릭은 한 번만 실행되고 같은 확정 결과로 귀결된다. `/cancel` 대상 목록과 `/resolve` 주문 버전을 확인 중 바꾸지 않는다. `/resume`은 D84의 허용 폭·정지 버전 검사를 유지하고 확인 시점 실제 적용 평가액을 응답한다. `/resolve` 문구는 사용자가 거래소에서 직접 확인했다는 명시적 동의이며 자동 확인으로 채우지 않는다. 콜백에는 `answerCallbackQuery`로 대기를 끝내되 미등록 사용자에게 응답 내용/팝업은 보내지 않는다.

### I5. 알림 묶음과 반복 경고 억제

같은 원인 키 = `(환경, 계좌, 알림 종류, 계약/전략, 관련 주문·복구 ID, 사유 코드)`다. 시각·가격·수량·변하는 문장 전체는 키로 쓰지 않는다. 새 원인의 첫 알림은 즉시 큐에 넣고, 설정된 고정 묶음 창 안의 반복은 횟수·최초/최종 시각·최신 상태로 누적한다. 창 종료 때 추가 반복이 있으면 요약 1건을 보낸다. 원인 해소와 새 정지 전이는 별도 이벤트로 즉시 알리고 반복 구간을 끝낸다. 같은 규칙을 로컬 경고에도 적용해 1초 로그 도배를 막는다.

체결은 exec_id별, 손절 체결도 고유 체결별로 보존하며 서로 다른 체결을 한 경고로 지우지 않는다. 명령 확인/최종 응답은 경고 묶음 대상이 아니다. 정지/저널 불확실 등 최초 긴급 알림을 일반 요약 뒤로 미루지 않는다. 묶음 창·재시도/전송 간격·큐 상한은 검증된 운영 설정으로 주입하고 위험 한도와 섞지 않는다. 묶음 상태/발송 ID를 저장해 재시작 중 중복을 줄이며 메모리 큐 상한 도달은 조용히 버리지 않고 미전송/탈락 수로 진단한다. DB 장애 중 보호 작업은 알림 저장/전송을 기다리지 않는다. 해당 구간의 비영속 반복 횟수는 재시작 시 보장되지 않음을 기록한다.

### I6. 전송 outbox·실패 분리

Trader·CommandService에는 Bot HTTP 호출 대신 로컬 enqueue 어댑터를 주입한다. 영속 명령/도메인 이벤트에서 발송 의도를 복원할 수 있게 하고 수신·발송 worker는 각각 감독/재시도한다. 폴링이 끝났다고 Trader 작업 그룹을 종료하지 않는다. 느린 Bot API·DNS·401/403·429·5xx·잘못된 JSON이 보호·경계·제어 tick을 막지 않아야 한다. 401/403은 반복 요청을 억제하고 로컬 health에 Telegram 장애를 표시한다. 429 retry_after와 유한한 타임아웃/백오프를 지키며 실패를 redaction한 alerts 이력에 남긴다.

발송 성공 확인 뒤 outbox를 완료 처리한다. sendMessage 응답 불명은 거래 명령 결과 불명과 분리한다. Bot API 발송의 서버 멱등 키가 없으므로 재전송 시 **메시지 중복 가능성**을 이력에 남기며 거래 명령을 다시 실행하지 않는다. 기존 raw 명령 JSON 전체 사용자 방송은 제거한다. 명령 응답은 원래 권한 있는 요청자의 채팅에만, 일반 경고는 설정된 수신자에만 보낸다(Q3). 시작/종료 알림도 같은 큐를 사용하고 종료 drain에는 기한을 둔다. 누락된 필수 자격 증명은 설정/부팅 오류, 부팅 후 Bot 통신 장애는 격리된 health 오류로 구분한다.

### I7. 키 만료 날짜·일일 요약

D75의 발급 화면 유효 기간을 사용하며 **3개월을 90일로 간주하지 않는다**. 정확한 만료 입력 계약은 Q1에서 확인한다. 날짜 계산은 UTC로 통일해 `만료 UTC 날짜 - 오늘 UTC 날짜`로 남은 날을 표시한다. 만료 날짜의 14일 전부터 날짜별 1회, 당일은 0일/당일 만료, 실제 만료 시각 이후는 만료됨으로 구분한다. 키 갱신은 새 발급/만료 세대이므로 이전 발송 이력을 승계하지 않는다. 토큰 만료를 Bybit API 키 유효 기간과 혼동하지 않는다.

일일 요약은 UTC 자정 펀딩/거래일 전환 커밋 뒤 직전 완료 거래일을 키로 한 번 생성한다. 자정 펀딩 대기 중에는 미확정 수치로 요약하지 않고 완료 후 지연 발송한다. D81 손익·거래·한도 사용률·AI 비용·경고를 제공하되 저장/산출 근거가 없는 값은 미확인으로 표시한다. 재시작 후에는 저장된 미전송 요약을 재개하며 같은 거래일 요약을 다시 만들지 않는다.

## 구현 전 PR에서 확인할 질문

1. **Q1 — 키 유효 기간 입력:** 현재 설정에는 `api_created_at`만 있고 유효 기간/만료일은 없다. 발급 화면의 정확한 **`api_expires_at` UTC 시각을 필수 비밀 아닌 설정으로 받는 안**을 제안한다. 발급일보다 이후인지 검증한다. 원문의 “발급일 + 유효 기간”을 이 명시적 만료 시각으로 표현해도 되는가? 기간 입력을 유지하려면 달/일 단위 및 월말 계산 규칙부터 확정해야 한다. 기본 90일은 넣지 않는다.
2. **Q2 — M1-06 수동 복구 인수:** M3-05 끝에는 replacement_exhausted·history_gap·missing_action_order 복구도 있지만 현행 `/resolve <orderLinkId>`는 UNKNOWN→NOT_FOUND만 지원한다. 별도 resolve 하위 형식/대상 종류·수동 증거 필드·워터마크/손절 재조회 절차를 명세에 먼저 정해야 한다. 이번에 이 세 경로까지 포함할지, 별도 명세 PR로 분리할지 확인이 필요하다. UNKNOWN용 버튼으로 보호 정지를 일괄 해제하지 않는다.
3. **Q3 — 채팅 범위:** 현재 수신 설정은 사용자 ID뿐이다. 최초 구현은 **허용 사용자와의 개인 채팅만** 명령/응답/일반 알림 대상으로 제한하는 안을 제안한다. 그룹·토픽을 허용하려면 별도 chat_id allowlist와 노출/확인 바인딩 계약이 필요하다. 허용 사용자라는 이유만으로 그룹에 계좌 정보를 보내지 않는다.
4. **Q4 — 장기 무수신 커서:** 공식 API는 일주일 이상 새 업데이트가 없으면 다음 update_id를 무작위로 정할 수 있다. 평생 max(update_id)만 저장하면 낮아진 ID를 놓칠 수 있다. **24시간 무수신 또는 재시작 시 offset 생략 조회로 미확인 배치를 다시 확인**하는 안을 제안한다. 음수 offset/대기 업데이트 삭제는 쓰지 않는다. 기존 inbox와 대조 후 새 배치 마지막 ID+1을 사용하며, 충돌 ID에 다른 명령이 오면 실행을 보류하고 진단한다. 별도 세대 식별자를 도입한다면 원래 request_id의 영속 멱등과 함께 먼저 계약을 고친다. 이 보수적인 충돌 시 수동 확인 정책으로 갈지 확인이 필요하다.

## 검증·완료 기록 계획

- 가짜 Bot API/시계와 합성 임시 DB만 사용한다. real token 조회·실 봇 호출·실계좌 주문·연구 DB·판정용 풀 접근은 없다. D103 실행 폴더/프로세스도 접근하지 않는다. 테스트 정리는 자신이 만든 태스크/자원만 대상으로 한다.
- 수신 저장 전/후, offset 원격 확인 전/후, 도메인 커밋 전/후, 응답 outbox 전/후, 발송 성공/불명에 장애를 주입한다. 재시작·중복/역순 배치·무수신 후 낮은 ID·상이 payload ID 충돌을 검사한다.
- 명령 5종과 미등록 사용자 감사/침묵, 인라인 확인 만료·다른 사용자/채팅·중복 클릭·이전 부팅 번호, D84 실제 적용 값, 취소 고정 대상/손절 보존, UNKNOWN 수동 확인을 검사한다. 웹 공통 서비스 회귀도 유지한다.
- 알림별 원인 키·고유 체결 보존·재시작 묶음·429/401/403/네트워크/잘못된 JSON·큐 상한·느린 전송 중 Trader 경계/보호/control.tick 진행을 검사한다. 토큰/키/서명 sentinel이 로그·DB·예외·alerts 어디에도 없는지 검사한다.
- UTC 날짜 경계·14일/13일/0일/만료 직후·윤년/월말·키 교체와 자정 펀딩 지연 요약을 검사한다. 단위 (a) 뒤 저장소/복구/경계/백테스트 회귀, (b) 뒤 전체 테스트·lint·format·mypy·지원 Python CI 결과를 남긴다.
- 실제 봇 수동 명령 5종+알림 1종은 자동 테스트 완료 후 **사용자와 함께** 진행한다. 이 절차를 수행하기 전 운영 완료로 표시하지 않는다.
