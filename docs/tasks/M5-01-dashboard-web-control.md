- 근거: **D106**(웹 제어 허용), D73(FastAPI + 간단한 HTML), D27(명령 범위), D48·D84(재개 재확인), D54(`/resolve`), **D105**(SQLite, 읽기 전용 연결), 03 7장, M3-05 명령 표, M1-03 `authorize_command`·`ResumeService`

## 목표

이 PC의 브라우저에서 운영 상태를 한눈에 보고, **텔레그램과 같은 명령만** 웹에서도 실행한다. 웹 제어는 텔레그램 명령과 **같은 처리 경로**를 지나므로 위험 검사·재확인 규칙을 건너뛸 수 없다.

## 일정 (사용자 결정 2026-11-11, 05의 M5 순서 예외)

- 화면은 지금 만든다. 저장소(M3-02)가 없으므로 처음에는 **가짜 데이터 공급원**으로 만들고, M3-02가 병합되면 SQLite 읽기 공급원으로 바꾼다.
- 제어 API(M5-01b)는 M3-05 명령 처리와 함께 만든다. 그 전까지 화면의 제어 버튼은 "Trader 미연결"로 비활성화한다.

## 구조

```
브라우저 ──HTTP──▶ Dashboard (127.0.0.1:대시보드 포트)
                      │ 읽기: SQLite 읽기 전용 연결 (D105, mode=ro)
                      │ 제어: Trader 제어 API 호출 (환경별 토큰)
                      ▼
                   Trader 제어 API (127.0.0.1:제어 포트) ──▶ CommandService ◀── 텔레그램
```

- Dashboard는 **DB에 쓰지 않는다.** 명령 기록(`commands`)도 Trader가 쓴다. 그래서 DB에 기록하는 프로세스는 계속 Trader 하나다(D105 전제).
- `CommandService`(M5-01b)는 텔레그램(M3-05)과 웹이 함께 쓰는 명령 처리기다. 권한 확인(`authorize_command`), 재확인 단계, 실행, `commands` 기록(`source` = telegram / web)을 한곳에서 한다.

## 명령 문맥 (PR #63 P2-3)

모든 명령은 `CommandService`에 아래 **명령 문맥**과 함께 들어간다. 문맥은 서버가 만든다. 브라우저가 보낸 actor·권한·환경 값은 믿지 않는다.

| 필드 | 텔레그램 | 웹 |
|---|---|---|
| `actor_id` | `telegram:<사용자 ID>` | `web:<운영자 ID>`. 운영자 ID는 **Trader 설정**(`[dashboard] operator_id`)에 있고, Trader가 제어 토큰을 확인한 뒤 붙인다. Dashboard 요청 본문의 actor는 무시한다 |
| `session_id` | 채팅 ID | Dashboard 로그인 세션 ID(Trader에는 세션 ID의 해시만 전달) |
| `environment`, `account_id` | Trader 자신의 값 | Dashboard가 읽기 DB의 `meta`에서 읽은 값을 요청에 담고, Trader가 **자신의 값과 비교해 다르면 거부**한다 |
| `request_id` | update ID | 브라우저가 명령마다 만든 무작위 ID(멱등 키) |

- 허용 actor 목록(`allowed_ids`)은 출처를 붙여 관리한다(`telegram:…`, `web:…`). `authorize_command`와 `ResumeService`는 웹도 예외 없이 이 목록으로 검사한다.
- 제어 토큰은 **환경별로 다르다**(`richletsgo/control-token-demo`, `richletsgo/control-token-live`). Trader는 자기 환경의 토큰만 받는다. 그래서 DEMO 화면이 잘못 연결된 LIVE Trader를 제어할 수 없다. 위의 환경·계좌 비교와 함께 이중으로 막는다.

## 확인 계약 (PR #63 P2-4)

재확인이 필요한 명령(`/resume`, `/cancel`, `/resolve`)은 텔레그램과 웹 모두 같은 규칙을 따른다.

1. **1단계(요청)**: 서버가 확인 기록을 만들어 저장한다. 내용은 명령 종류, 대상, 환경·계좌, actor·세션, 상태 버전, 만료 시각(60초)이다.
   - `/resolve`: 대상 orderLinkId 하나. 상태 버전은 그 주문의 현재 상태와 이벤트 수다.
   - `/cancel`: **1단계 시점의 미체결 진입 주문 목록을 고정**한다. 확인 화면에 그 목록을 보여 주고, 실행은 그 목록 안에서 아직 미체결인 것만 취소한다. 그사이 새로 생긴 주문은 취소하지 않는다(화면 문구: "아래 N건만 취소합니다").
   - `/resume`: 기존 `ResumeService`의 `ResumePrompt`(pause_revision, 기록용 최고점, 평가액 허용 폭)를 그대로 쓴다.
2. **2단계(확인)**: 확인 번호를 **원자적으로 소비**한다. 같은 번호의 두 번째 사용은 실행하지 않고 첫 결과를 돌려준다. 실행 직전에 최신 상태를 다시 검사한다. 상태 버전이 바뀌었으면(주문 상태 변화, `/resume`의 pause_revision·평가액 허용 폭 위반 등) 실행하지 않고 다시 요청하게 한다.
   - 확인은 같은 출처·같은 세션·같은 actor·같은 환경에서만 가능하다. 텔레그램에서 받은 번호를 웹에서, 다른 세션에서 쓰면 거부한다.
3. **멱등과 응답 유실**: 확인 소비, 명령 실행 의도, `request_id`를 `commands`에 한 트랜잭션으로 기록한 뒤 실행한다. 같은 `request_id`가 다시 오면 다시 실행하지 않고 기록된 결과(진행 중이면 "처리 중")를 돌려준다. 저장소가 커밋 결과 불명(M3-02)이면 명령은 "결과 확인 중"으로 보류하고, 판정이 끝나기 전에는 다시 실행하지 않는다.
4. 재시작하면 미사용 확인 번호는 모두 무효가 된다(메모리에만 두거나, 저장한다면 시작 시 폐기).

재확인이 없는 `/pause`도 `request_id` 멱등 규칙은 같다.

## 보안

| 위험 | 대책 |
|---|---|
| 외부에서 접속 | 두 서버 모두 `127.0.0.1`에만 연다. `0.0.0.0` 등 다른 주소 설정은 시작 시 거부한다 |
| DNS 재바인딩 | `Host` 헤더가 `127.0.0.1:<포트>` 또는 `localhost:<포트>`가 아니면 거부 |
| 다른 사이트가 몰래 요청(CSRF) | 제어 요청은 POST만 허용. 세션마다 CSRF 토큰을 확인하고, `Origin`이 대시보드 주소가 아니면 거부. 쿠키는 `HttpOnly`, `SameSite=Strict` |
| 다른 사이트에 끼워 넣기(클릭재킹) | `Content-Security-Policy: frame-ancestors 'none'`, `X-Frame-Options: DENY` |
| 화면에 스크립트 주입(XSS) | 아래 "출력 규칙" |
| 로그인 없이 제어 | **제어는 접근 코드로 로그인한 세션만** 가능. 접근 코드는 자격 증명 관리자(`richletsgo/dashboard-access`)에 두고 화면·로그·설정 파일에 남기지 않는다. 보기만 하는 화면은 로그인 없이 열린다. 로그인 실패가 연속 5회면 10분 잠근다 |
| Dashboard ↔ Trader 위조, 환경 혼동 | 환경별 제어 토큰 + 환경·계좌 비교(위 "명령 문맥"). 토큰은 시작 시 읽고 응답·로그에 넣지 않는다 |
| 실수로 누름 | 위 "확인 계약"의 2단계 확인 |
| 원격에서 모르게 실행 | 웹에서 실행한 명령은 결과와 함께 **텔레그램으로도 알린다** |

**로그인 세션 (PR #63 P2-5)**

- 세션 ID는 `secrets.token_urlsafe(32)` 이상의 난수다. 서버가 세션 표를 메모리에 들고 만료를 서버에서 검사한다(쿠키 만료만 믿지 않음).
- 로그인에 성공하면 세션 ID를 **새로 발급**한다(로그인 전 ID 재사용 금지).
- 만료: 유휴 15분, 절대 8시간(설정 가능, 기본값 고정). 만료되면 다시 로그인해야 한다.
- 로그아웃 버튼으로 즉시 무효화한다. 그 세션의 미사용 확인 번호도 함께 무효화한다.
- Dashboard를 재시작하면 모든 세션이 무효가 된다(세션 표를 메모리에만 둠).
- 접근 코드를 바꾸면(Dashboard가 시작할 때와 주기적으로 코드 해시를 확인) 모든 세션과 미사용 확인 번호를 무효화한다.

**출력 규칙 (PR #63 P2-6)**

명령 기록, 알림, 거래소 오류 문구, AI 근거는 신뢰할 수 없는 문자열로 다룬다.

- Jinja2 자동 이스케이프를 끄지 않는다. 신뢰할 수 없는 값에 `|safe`나 원본 HTML 삽입을 쓰지 않는다.
- JSON으로 갱신하는 부분은 `textContent` 등 텍스트로만 넣는다. `innerHTML`에 데이터 값을 넣지 않는다.
- 서버가 만드는 SVG의 텍스트·속성 값도 이스케이프한다.
- `Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'`. 인라인 스크립트와 외부 스크립트·CDN을 쓰지 않는다.

**한계 (PR #63 P3)**: `mode=ro`는 그 SQLite 연결의 쓰기를 막을 뿐 운영체제 권한 분리가 아니다. 같은 Windows 사용자 권한으로 도는 악성 프로그램은 DB 파일이나 자격 증명 관리자에 직접 접근할 수 있다. 이 화면의 보안 대책은 브라우저 경유 공격(다른 사이트, 실수, 외부 접속)을 막는 것이고, 같은 사용자 권한의 악성 프로그램은 막지 못한다.

## 명령 범위 (D106: 텔레그램과 같음)

| 명령 | 웹 | 재확인 |
|---|---|---|
| 상태 보기 | 대시보드 화면 자체 | 없음 |
| 신규 진입 정지 (`/pause`) | 버튼 | 없음 |
| 재개 (`/resume`) | 버튼 → `ResumeService` 재확인 화면(기록용 최고점, 현재 평가액, 낙폭, 다음 정지 수준, 허용 폭) → 확인 | 필수 (D48·D84) |
| 미체결 진입 주문 취소 (`/cancel`) | 버튼 → 고정된 대상 목록 확인 → 확인. 손절은 유지 | 필수 |
| UNKNOWN 수동 확정 (`/resolve`) | 주문 목록의 UNKNOWN 행에서 실행 | 필수 (D54) |

**넣지 않는 것**: 주문 넣기, 전체 청산(D27: Bybit 앱에서), 위험 한도·설정 변경, API 키 관리, 서비스 시작·종료.

## 화면 (M5-01a)

모든 시각은 한국 시간으로 보여 주고, 내부 값은 UTC 그대로 둔다. 환경(DEMO / LIVE)을 화면 맨 위에 항상 크게 표시하고, LIVE는 색을 달리한다.

1. **개요**: 정지 상태와 이유, 평가액·오늘 손익(D81)·낙폭, 한도 사용률(L1~L7), 마지막 확정 봉·체결 시각, Trader 연결 상태, 키 만료까지 남은 날
2. **포지션**: 전략별 장부 포지션, 손절가, 손절까지 거리, 거래소 손절 수량 = 보유량 여부
3. **평가액 그래프**: 평가액과 낙폭(기간 선택: 1일·7일·30일·전체)
4. **주문·체결**: 최근 주문(상태별 필터, UNKNOWN 강조), 체결 목록
5. **기록**: 알림, 명령(출처 telegram/web, 결과), 정지 이력
6. **결정과 AI**: decision별 AI 점수·근거·비용 누계(M4 이후. 그 전에는 "AI 비활성" 표시)
7. **제어**: 위 명령 표의 버튼(로그인 세션만, 재확인 포함)

- 화면은 서버에서 HTML을 만들고(Jinja2), 자동 새로고침은 짧은 주기(예: 10초)의 가벼운 JSON 조회로 한다. 그래프는 서버가 만든 SVG로 그려 외부 CDN 없이 동작하게 한다.
- 휴대폰 너비에서도 깨지지 않게 만든다(같은 PC 안에서만 접속하더라도 창을 좁혀 볼 수 있으므로).

## 기술

- FastAPI, Uvicorn, Jinja2 (런타임 의존성 추가. 이유: D73에서 정한 웹 구성). 다른 프레임워크·빌드 도구는 쓰지 않는다.
- 데이터 공급원은 인터페이스(`DashboardSource`)로 두고 가짜 구현과 SQLite 읽기 구현을 바꿔 끼운다. 화면 코드는 DB를 직접 열지 않는다.
- Windows 서비스 `RichLetsGo-Dashboard`(M3-06)로 실행한다. Trader가 꺼져 있어도 화면은 뜨고, 제어 버튼만 비활성화한다.

### M5-01b (제어 API)
- [ ] 텔레그램과 웹이 같은 `CommandService`를 거침. 웹 경로에만 있는 실행 분기가 없음
- [ ] actor는 Trader가 토큰과 설정으로 정함. 요청 본문의 actor는 무시. `web:` actor도 `allowed_ids` 검사를 받음
- [ ] 환경·계좌 불일치, 다른 환경의 토큰 → 거부
- [ ] 재확인 명령에 확인 없이 실행되는 경로가 없음. 확인 번호의 대상 고정(다른 orderLinkId·다른 명령에 사용 거부), 만료, 다른 세션·다른 출처(telegram↔web) 사용 거부, 동시 두 번 확인 → 한 번만 실행
- [ ] 상태 버전 변경 시 실행하지 않음(`/resume`은 기존 pause_revision·평가액 허용 폭 검사 그대로). `/cancel`은 1단계 목록 밖의 주문을 취소하지 않음
- [ ] 같은 `request_id` 재전송 → 재실행 없이 기존 결과. 커밋 결과 불명 → 보류, 재실행 없음
- [ ] 토큰 없거나 틀린 요청 거부, `127.0.0.1` 외 바인딩 거부
- [ ] 모든 웹 명령이 `commands`에 `source=web`으로 기록되고 텔레그램 알림이 나감
- [ ] 금지 명령(주문·청산·설정 변경)에 해당하는 API가 존재하지 않음

## 검토 포인트

- Dashboard가 DB에 쓰는 경로가 없는지
- 제어가 텔레그램 경로와 다른 규칙으로 실행될 여지가 없는지
- 비밀 값(접근 코드, 제어 토큰)이 어디에도 출력되지 않는지
- 외부 노출 설정이 실수로라도 가능하지 않은지
- 신뢰할 수 없는 문자열이 HTML·SVG로 해석되는 경로가 없는지
