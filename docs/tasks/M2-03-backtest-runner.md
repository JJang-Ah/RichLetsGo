## 범위

### 만들 것 (`src/richletsgo/backtest/` 신설 — 03 모듈 목록에 이미 추가됨)

1. **실행 단위** `BacktestRun`
   - 입력: 데이터 저장소(M2-01), 기간(UTC 시작·끝), S1 전략 종류와 매개변수, S2 전략 종류와 매개변수, 위험 프로필, 수수료·슬리피지 설정, 시작 평가액, 계약 목록.
   - 출력: 거래 목록, 주문·체결 기록, 일별·시간별 평가액, 정지 상태 변화, 설정 요약.

1-1. **데이터 완전성 검사** (D77, 실행 전)
   - 두 계약 모두 [시작 − 워밍업, 끝) 범위의 일봉·1시간봉이 빠짐없이 있는지, 기간 안 펀딩 기록이 끊기지 않았는지 검사한다(D87: 이웃한 기록 간격이 수집 시점 펀딩 주기보다 길면 빠진 것).
   - 하나라도 빠지면 실행하지 않고 `INVALID_DATA`(빠진 계약·주기·시각 목록 포함)를 돌려준다. 빈 봉을 만들거나 펀딩을 0으로 채우지 않는다.
   - 한 계약만 빠져도 전체가 무효다(계좌 단위 한도가 두 계약에 걸치기 때문).

1-2. **구간 끝 처리** (D78): 실행 범위 [시작, 끝)에서 마지막 경계 `끝 − 1시간`에 신규 진입을 막고, 열린 진입 주문을 취소하고, 남은 포지션의 청산 주문을 낸다. 청산은 범위 안의 마지막 봉 [끝 − 1시간, 끝)의 시가에 체결된다. 끝 시각에 아직 포지션이 남아 있으면(예외) 마지막 봉 종가로 평가하고 결과에 표시한다. 범위 밖 봉은 읽지 않는다.

2. **시간 순서** (04 3.1절 경계 시각 처리 순서, D76) — 1시간 경계 T마다 아래 순서를 **고정**한다.
   1. 가상 거래소가 T에 끝나는 봉 동안의 체결·손절을 처리하고 이벤트를 낸다 → OMS·장부에 반영.
   2. T에 저장된 펀딩 기록이 있으면(D87) 그 시점 보유 포지션에 펀딩 정산 → 장부 반영.
   3. T가 UTC 00:00이면: 펀딩 후 지갑 잔고로 거래일 기준값 저장(D72) → 일일 정지 해제 → 곧바로 L5·L6 재검사(넘어온 미실현 손실로 다시 정지될 수 있음).
   4. 마감 봉으로 신호 계산: S1(일봉, 00:00일 때만) → S2(1시간봉). 계약은 BTCUSDT → ETHUSDT.
   5. 신호를 위험 게이트·포트폴리오에 넣어 주문 생성.
   6. 주문은 T부터 시작하는 봉의 시가부터 체결 가능.
   - 시계는 `ManualClock`으로 옮긴다. 실제 시계를 쓰지 않는다.

3. **연결**
   - 가상 거래소: M1-05 `SimulatedExchange`(체결 규칙 D49, Partial 손절 부착, 펀딩).
   - 위험·장부·청산: M1-03, M1-04 그대로. `ai.mode=disabled`.
   - 저장소: M1-02 메모리 UoW 또는 SQLite 구현. 실행이 끝나면 결과를 SQLite 결과 파일에 저장한다(`paths.backtest.backtest_results_dir`).
   - 장애 주입은 쓰지 않는다(정상 경로).

4. **위험 프로필**
   - `RiskLimits`(M1-03)를 설정의 연구용 프로필에서 만든다. 결과 파일과 보고서에 그 값을 함께 저장한다. 코드에 기본값을 두지 않는다.
   - **MMR (D79)**: M2-01이 저장한 `risk_limit_tiers`에서 계약별 1단계 MMR을 쓴다(단계별 MMR을 따로 모델링하지 않음).
   - **1단계 상한 검사는 계약 합산 기준**이다: 위험 게이트의 같은 트랜잭션 안에서 `기존 보유 + 미반영 체결 + 진입 예약 + 귀속 보류 체결 + 이번 승인량`을 계약 단위로 합친 명목 금액(02 2.1절 노출과 같은 보수적 가격)이 1단계 상한을 넘으면 그 진입을 거절하고 기록한다. 전략별로 따로 보지 않는다. 저장된 단계 정보가 없으면 실행을 거절한다. 쓴 MMR 값과 `captured_at`을 결과 메타에 남긴다(수집 시점 값이라 과거 시점과 다를 수 있음을 표시).

5. **결과 기록**
   - 거래: 전략, 계약, 진입·청산 시각·가격, 수량, 수수료, 펀딩, 손익, R 배수(손익 ÷ 진입 시 허용 손실), 청산 사유(손절, 평균 복귀, 최대 보유, 추세 전환, 추적 손절).
   - 평가액: 1시간마다, 거래일 경계 기준값(D72).
   - 메타: 데이터 범위와 해시, 설정 해시, git 커밋, 실행 시각.

## M2-02 연결 보완 (PR #22 검토, 2026-10-23)

- Wilder RSI·ATR은 마지막 10×n개 봉에서 seed부터 계산한다. `strategy.candidates.required_bars(params)`가 직전 지표까지 포함한 최소 평가 창을 반환한다. 운영 시작 시 최소 그 수의 마감 봉을 적재하며, 백테스트는 한 번 검증한 전체 이력에서 `through(start, lookback=required_bars(params))`로 잘라 평가한다. 이력 전체 접두를 매번 만들지 않는다.
- S1 결과가 EXIT면 청산 라우터로 전달하고 그 봉에서는 `trail_stop`을 호출하지 않는다. 목표 후보가 종가를 이미 넘어선 경우 기존 목표를 유지하며 ENTRY를 내지 않는 규칙이다. 최초 판단에 직전 목표가 없으면 S1State.stop_price는 None일 수 있다. 추세 자체는 유지하며 다음 유효한 판단에서 목표와 ENTRY가 만들어진다.


## 구현 연결 계약 (2026-10-23)

- `backtest.config.load_research_config(Path)`는 backtest 환경만 받는다. D88의 research_risk와 selection 구조는 유지하며 selection 해석은 M2-04가 맡는다. 재시도·동기화 정책은 별도 `[backtest.execution]`에서 필수 입력받는다. 상대 경로는 설정 파일 부모 기준이다.
- `backtest.runner.BacktestRun(...).execute(store, results_dir=..., journal_dir=...)`는 비동기 실행 API다. S1/S2 매개변수, UTC 정시 시작·끝, 실행 시각과 코드 커밋을 호출자가 전달한다. 실제 시계와 네트워크 호출은 없다. 재현 가능한 호출 예시는 `tools/benchmark_backtest.py`를 참고한다.
- 연구 수수료 예시 taker=0.00055, maker=0.0002는 2026-10-23 확인한 [Bybit 공식 기본 VIP 0 선물 수수료표](https://www.bybit.com/en/help-center/article/Trading-Fee-Structure)와 일치한다. 개별 계정/지역의 실제 요율은 별도 확인한다.
- 레버리지는 연구 상한·상품 상한·1단계 상한 중 최솟값이다. MMR/상품 규칙은 수집 시점 스냅샷이며 과거 변경과 단계별 강제청산은 재현하지 않는다. 시간봉 경계가 아닌 펀딩은 현재 실행기가 처리할 수 없으므로 INVALID_DATA로 보고한다.
- SQLite 결과는 거래·주문·체결·위험 결정·평가액·정지·처리 순서·메타를 저장한다. 순손익과 R은 수수료와 펀딩을 포함한다. 종료 잔여 포지션은 INCOMPLETE와 마지막 종가 평가로 남긴다. 실행 중 보호 저널은 격리된 임시 폴더를 사용한다.
- 결과 해시와 설정 해시에서 실행 시각만 제외한다. 같은 입력은 같은 파일 이름을 쓰며 기존 결과가 있으면 최초 실행 메타를 보존한다. 데이터·매개변수·코드 커밋은 해시에 포함한다.
- 공통 동기화기 보완: 청산 outbox의 QUERY_STOPS는 같은 시각의 이전 조회를 새 조회로 인정하지 않는다. 새 스냅샷 revision이 생기기 전에는 acknowledge하지 않아 다음 tick에서 검증을 계속한다. 이를 생략하면 청산 에피소드가 VERIFYING에 머물러 이후 진입이 차단됐다. S1-A/B 손절 후 다음 날 재진입 회귀로 확인한다.
- 3년 부하 측정은 합성 OHLC·펀딩으로 수행한다. 실제 수집 시장 데이터의 3년 실행/성과 확인은 별도이며, 이 항목의 완료 여부와 수치는 PR에 구분해 기록한다.
