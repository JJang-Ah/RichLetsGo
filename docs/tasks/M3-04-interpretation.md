## 조립 해석

1. **한 Trader·한 계좌 잠금.** 설정·키·DB·게이트·포트폴리오·동기화기·제어 서비스를 한 프로세스에서 주입한다. `RiskGate.account_lock`을 위험 상태 관측/게시와 명령에 공유한다. 외부 REST/WS·텔레그램·커밋 결과 조회는 잠금 밖에서 기다리고, 잠금 재획득 후 상태 버전·요청 소유권을 재검사한다. 필수 UoW I/O는 M3-02 예외다. 별도 Trader나 자동 서비스 설치는 만들지 않는다.
2. **부팅과 재연결.** 설정·환경·스키마 검증 → 저장 저널 합치기 및 정지/추적기 복원 → 개인 WS 선구독·버퍼 → REST 스냅샷·재생 → 보호·안정화 → 시세 WS·필수 이력 → 진입 허용 순서를 지킨다. 추적기 복원은 새 관측 전 완료하며, 부팅 중 추가된 정지는 보존한다. 기존 메서드가 `sync` 정지를 먼저 해제해도 조립층의 별도 준비 정지를 마지막까지 유지한다. 단계 실패/재연결 때 진입은 닫고 보호는 계속한다. 이미 확정된 resume를 재생하지 않는다.
3. **전략·source.** AI disabled, M2-02 필수 매개변수/required_bars 검증을 재사용한다. D97 주·부 보고서, S2 enabled=false 계약을 설정 로더에 구현한다. 보고서는 명시된 경로의 JSON만 읽고 본문 해시·PASS·같은 선택 쌍 및 공통 등록/데이터/구간을 검증한다. 실제 연구를 재실행하거나 미관측 자료를 읽지 않는다. manual은 개발 연결용이며 운영 승인으로 취급하지 않는다. S2 비활성은 신호·주문 생성 자체를 건너뛴다.
4. **봉 장벽·공통 처리.** 경계 T의 BTC/ETH 1시간봉, UTC 자정에는 일봉까지 모아 처리한다. 중복/역순 입력을 버퍼링하고 기한 뒤 REST 보충, 최종 누락은 해당 계약의 신호만 생략한다. 백테스트 실행기에서 공통 경계/전략 처리 함수를 추출해 두 실행기가 실제로 호출하도록 한다. 의미 변경 없이 기존 합성 결과를 비교한다. 오래된 경계는 회계는 처리하고 신호/위험 판단만 생략한다.
5. **경계 원자성.** 확정 입력, 체결 시각 <T의 전략 보유량 스냅샷, 펀딩, 자정 준비 입력, 자정 반영, 신호 출력·전략 상태를 명세 단계별로 같은 UoW의 체크포인트와 저장한다. 커밋 전 실패는 단계 전체 롤백, 성공 뒤 실패는 저장 출력 재사용이다. 준비된 자정 계좌 스냅샷은 불변으로 재사용한다. 아직 결정이 없는 신호만 최신 평가액·정지·예약·시세로 게이트를 다시 검사한다. 주문 전송은 단계 체크포인트가 아니라 기존 OMS/저널/UNKNOWN이 소유한다.
6. **펀딩.** 공개 율 대신 계좌 펀딩 ID·정산 시각·금액을 조회하는 어댑터 계약을 추가하고 가상 거래소도 같은 입력을 주입한다. M1-04 funding에 settled_at을 전달해 정산 시각 보유량으로 배분한다. 이후 포지션 변경이나 청산은 귀속을 바꾸지 않는다. 보유량 0 비용은 미배분으로 기록·알린다. 자정 보유 계약의 펀딩이 늦으면 start_day와 신규 진입만 보류하고 보호/축소/취소와 제어 처리는 계속한다. 자정 정산은 전날 귀속이다. 정산 이후 계좌 스냅샷을 준비하고 다시 찍지 않는다.
7. **주기 배선.** 동기화기의 WS 처리·손절/outbox·만료 진입 취소를 주기 실행한 뒤 `CommandService.tick()`으로 취소 대상의 실제 종결/재시도/알림을 처리한다. 경계 입력 또는 펀딩 대기가 실행 루프를 독점하지 않게 한다. REST 완전 대조는 명세의 1분 주기, 상품/위험 단계·수수료 점검은 하루 1회다. 빠른 보호/제어 tick 주기는 설정으로 주입하고 값·검증을 문서화한다. 가짜 시계로 주기를 검증하며 폴링 sleep에 기대는 테스트는 쓰지 않는다.
8. **보호·health·종료.** 체결 후 실제 강제청산가로 D62를 재검사하고 위반 시 알림·축소한다. 보유 손절은 계속 거래소에 남긴다. health는 localhost에 마지막 경계·WS·DB 커밋·정지 요약만 노출하고 키·상세 설정을 내지 않는다. 종료 시 진입 정지 → 진행 UoW 회수 → WS/작업 정리 순서이며 자동 전체 청산은 하지 않는다. M3-05 메시지 전송·M3-06 서비스 설치는 주입 경계로 유지한다.
9. **개발과 운영의 분리.** 이 PR 검증은 가상 거래소·가짜 시계·임시 DB/저널·합성 보고서로 한다. 실제 24시간 데모 시험과 사용자 선택 PASS 전략은 별도의 운영 완료 조건으로 남긴다. 코드 구현만으로 M3-07 완료나 실거래 활성화를 선언하지 않는다. 구현 중 원문으로 결정되지 않는 사항은 이 PR에 질문하고 계약을 임의로 바꾸지 않는다.

## PR #72 P2: 코드 전에 고정하는 보완 사항

1. **준비 게이트:** 조립층 준비 정지는 새 저장 정지 종류가 아니라 저장하지 않는 메모리 진입 게이트다. 부팅·재연결마다 닫고 4.3의 11단계가 끝날 때만 연다. 안정화 불일치 횟수 초과면 알림 후 닫힌 상태를 유지하며, 체결 워터마크가 API 조회 가능 범위보다 오래됐으면 자동 복구하지 않고 정지·알림만 한다.
2. **자정 재촬영:** ③-1 준비 레코드 커밋 전에는 정산 시각보다 이른 계좌 스냅샷을 버리고 재촬영한다. 커밋 성공 뒤에는 준비 입력이 불변이며 재촬영하지 않는다. 준비 커밋 결과 불명은 판정 전 재촬영하지 않고, 롤백으로 판정됐을 때만 다시 준비한다.
3. **자정 대기 범위:** 자정 보유 계약의 펀딩을 기다리는 동안 **모든 계약**의 신규 진입을 보류한다. 기한 뒤 REST 조회에도 없으면 알림을 반복하고 보류를 유지하며, 손절·축소·청산·취소와 제어 tick은 계속한다.
4. **추출 회귀 기준:** 기존 백테스트 테스트는 수정 없이 전부 통과해야 하고, 추출 전·후 같은 합성 캠페인의 정규화 보고서 본문 바이트와 `codec.digest`가 모두 동일해야 한다. 가변 실행 시간 같은 본문 밖 메타데이터를 본문 비교에 섞지 않으며 실제 연구·판정용 가격 자료로 비교하지 않는다.
5. **D97/source 목록:** `report_path`와 `secondary_report_path`는 설정 파일 위치 기준 상대 경로로 해석한다. S1 source는 주 S1B 본문 해시, S2 source는 부 S1B-S2P 본문 해시이며 JSON 본문 `codec.digest`를 재계산한다. 주 PASS는 항상 필수이고 S2 켬에는 부 PASS와 두 보고서의 사전 등록 id·sha256·data_hash·종목·판정 구간 일치, S1이 주 선택값이면서 부 선택 쌍에 포함됨을 확인한다. `secondary_report_path`는 S2 켬에만 받고, S2 `enabled=false`에는 enabled 외 필드와 secondary_report_path를 거절하며 enabled 생략은 true다. 예전 `m2-04:` source는 거부하고 source는 설정 해시·config_versions에 남긴다. 기존 단일 보고서 계약은 D97 두 보고서 계약으로 대체하며 manual은 개발용이다.
6. **보호·재시작:** `confirm_stop_snapshot`은 전체 손절 조회 성공 시에만 조회 **시작** 시각으로 호출하고, 계좌 동기화 완료 뒤 `recover_system_pause`를 시도한다. 재시작 때 만료 진입의 잔량 취소 처리를 진입 게이트를 열기 전에 수행하며 응답 불명은 기존 UNKNOWN 규칙으로 보류하고 부분 체결 보유는 유지한다.
7. **request_id 이행:** 아래 V002의 추가 매핑 테이블로 출처별 외부 ID와 내부 저장 키를 분리한다. V001의 기존 commands/targets/복구·저널·알림·outbox 행과 식별자는 다시 쓰지 않는다. 기존 요청 재시도는 같은 레코드로 돌아가며 출처가 다른 같은 외부 ID는 독립된 새 요청으로 저장한다.

### V002: 출처별 요청 식별자 이행

- 마이그레이션 이름은 `V002__command_identities.sql`, 스키마 버전은 **2**로 고정한다. 현행 V001은 변경하지 않는다. 새 DB는 V001→V002 순서로 적용하고, 기존 V1 DB는 명시적 migrate로만 올린다. 운영 시작은 버전 불일치 시 거부한다. 배포용/패키지용 마이그레이션을 함께 유지한다.
- 새 테이블 `command_identities(account_id TEXT, source TEXT, external_request_id TEXT, storage_key TEXT)`를 추가한다. 기본 키는 `(account_id, source, external_request_id)`, `(account_id, storage_key)`는 UNIQUE다. source는 web/telegram만 허용하며 빈 값/알 수 없는 출처는 이행 실패로 끝낸다. 기존 commands의 source 값이 출처의 근거다.
- 이행 트랜잭션에서 기존 commands의 `(account_id, source, request_id)`를 읽어 동일 값의 external_request_id와 기존 request_id 그대로의 storage_key를 매핑 테이블에 **추가**한다. 기존 commands·command_targets의 기본 키/내용과 recovery 데이터·미전송 알림·취소 outbox/저널의 키·payload는 그대로 보존한다. 불일치·충돌은 추정하지 않고 롤백한다. 이행과 버전 갱신은 한 트랜잭션이다.
- 새 요청은 source-qualified 외부 식별자로 먼저 매핑을 찾는다. 없으면 계좌 잠금/UoW 안에서 충돌 없는 새 내부 키(UUID 기반, 기존 commands 및 매핑과 유일성 확인)를 할당해 매핑·명령 의도를 같은 트랜잭션에 저장한다. request_id 원문을 보낸 웹/텔레그램 계약은 유지하고 내부 저장 키는 별도 필드로 다룬다. 내부 commands/targets/복구 레코드와 새 알림·outbox 참조에는 같은 storage_key를 사용한다. 결과 불명일 때 새 키를 재발급하지 않는다.
- 이행된 기존 명령은 기존 키로 조회·복구·알림 전송·취소 추적을 이어 간다. 다른 source로 bare request_id를 찾는 fallback은 두지 않는다. 메모리 pending/prompts도 `(source, external_request_id)`로 구분한다. 확인 번호의 actor/세션/계좌/출처 바인딩과 외부 재시도 ID를 바꾸지 않는다.
- 합성 V1 DB의 종결/처리 중/취소/미전송 알림을 V2로 올려 기존 데이터 불변과 재시도 멱등·재시작 복구를 검사한다. 같은 외부 ID의 web/telegram 동시 요청, 이행 중 실패 롤백·재실행, 결과 불명 중 중복 키 발급 금지를 검증한다.
