## 범위

### 만들 것

1. **동기화 절차** `Synchronizer` (`oms/`, D47) — 03 4.3절 1~11단계 중 M1 범위
   - 동기화 동안 `ENTRY_PAUSED_SYSTEM(sync)`.
   - 개인 이벤트 스트림 먼저 구독, 이벤트는 버퍼에만 쌓음.
   - REST 스냅샷: 잔고, 포지션, 미체결(조건부 포함), **마지막 저장 체결 시각 − 여유 시간**부터의 체결 내역.
   - 스냅샷 반영(execId 중복 제거, 상태 규칙) → 버퍼 재생 → 보호 확인(전략별 손절 = 보유, 부족분 `PROTECT`, 초과분 취소, 미완료 `CloseIntent` 재개) → **안정화 확인**(포지션 재조회 = 장부; 다르면 스냅샷부터 반복, 횟수 초과 시 정지 유지·알림) → 정지 해제.
   - 마지막 체결 시각이 조회 가능 범위 밖이면 자동 복구하지 않고 정지 유지·알림(범위는 설정값).
   - 시작과 재연결에 같은 절차를 쓴다.
   - **재시작 시 주문 정리 (D60)**: `CREATED`로 남은 주문은 `ABORTED`(보낸 적 없음, 예약 해제, 신호 재평가 없음, 체결 없는 에피소드 종료), `SUBMITTED`로 남은 주문은 `UNKNOWN`으로 바꿔 5.3절 해소에 넘긴다.
   - **귀속 보류 해소 (D61)**: 보류 체결이 기한을 넘기면 거래소 주문 ID로 조회해 결과를 M1-02에 넣는다.
   - **주문 전송기**: 주문을 보내기 직전 `SUBMITTED` 커밋 → 커밋 성공 후에만 `place_order` 호출. 이 순서를 한 함수에 모은다.

2. **로컬 저널** `ProtectiveJournal` (`oms/` 또는 `storage/`, D45·D55)
   - 디렉터리를 주입받는다. 추가 전용 JSON Lines, 한 줄마다 flush + `os.fsync`.
   - 레코드 필드: `operation_id`, `phase`(requested/result), `seq`, `op_type`(create/amend/cancel/close), `target`(orderLinkId, orderId), `request`, `result`, `ts` (03 5.4절 표).
   - **보호·축소 작업만** 저널을 쓴다. 노출 증가 주문(진입)은 저장소 커밋이 실패하면 보내지 않는다.
   - 저장소 장애 모드: `UnitOfWork` 커밋이 실패하면 `ENTRY_PAUSED_SYSTEM(db)` + 보호 작업은 저널 기록 후 전송. 저널 기록도 실패하면 **보호 작업은 그래도 보내고** 알림.
   - 재생: `seq` 순서로 `(operation_id, phase)` 단위 멱등 반영. `requested`만 있는 작업은 종류별로 거래소에서 결과 확인(create/close: orderLinkId 조회, amend: 현재 trigger 비교, cancel: 상태 확인). 그다음 동기화 절차 실행.
   - 반영 완료 파일은 보관 폴더로 이동.
   - **손상 처리 (D63)**: 프로세스 시작마다 새 구간 파일(`journal-<번호>.jsonl`)에 쓴다. 마지막 줄만 손상(줄바꿈 없음, 잘린 JSON·UTF-8)이면 그 줄을 `.partial`로 옮겨 보관하고 무시. 중간 줄 손상이면 자동 재생 중단, 신규 진입 정지, 알림. 다음 seq = 모든 구간의 정상 레코드 최대 seq + 1.
   - `requested` 레코드는 fsync가 끝난 뒤에만 주문을 보낸다(잘린 `requested` = 보내지 않은 작업).

3. **V0 통합 테스트** (`tests/v0/`)
   - 04 2장 V0 표의 **모든 행**을 `SimulatedExchange` + `FaultPlan` + 메모리 저장소로 재현한다. 단위 테스트(M1-02~05)로 이미 덮인 행은 통합 경로로 한 번 더 확인한다.
   - "강제 종료"는 Trader 객체를 버리고 같은 저장소·저널·가상 거래소로 새 객체를 만들어 동기화를 돌리는 방식으로 재현한다.
   - "장시간 미복구"는 `ManualClock`으로 시간을 옮기고 그 사이 가상 거래소에서 손절이 발동하는지 확인한다(손절은 거래소 쪽이라 프로세스가 없어도 동작해야 함).
   - `docs/tasks/M1-06-v0-matrix.md`에 **V0 표 행 ↔ 담당 작업 ↔ 테스트 이름** 대응표를 만든다. 담당은 [M1-00](M1-00-overview.md)의 "V0 담당 표"를 따른다. M1 담당 행은 테스트가 반드시 있어야 하고, M3·M4 담당 부분(텔레그램 봇, Watchdog 알림 전송, 실제 AI 호출, 실제 시세 수신)은 "M1에서는 정책만 검증, 외부 연동은 Mx" 로 표시한다. 정책을 스텁으로 통과시키지 않는다.

4. **기존 코드 삭제** (D39)
   - `trading_lab/`, `tests/test_core.py` 삭제. 그 아이디어(통화 일치는 USDT 단일 계약으로 대체, Decimal 강제, reduce-only 방향, 레버리지로 위험 축소 안 함)가 M1-01·M1-03 테스트에 있는지 PR 설명에 대응표로 적는다.
   - `pyproject.toml`의 pytest `pythonpath = ["."]`, ruff `extend-exclude = ["trading_lab"]` 제거.
   - README·REVIEW.md의 관련 문구 갱신(REVIEW 발견 1~8 반영 상태 표시).

## 완료 조건

- [ ] V0 표의 모든 행이 대응표에 있고, M1 담당 행(정책 부분 포함)은 모두 테스트가 있음
- [ ] 재시작 경계 테스트: decision·CREATED 커밋 직후 종료 → 재시작 시 `ABORTED`, 같은 신호로 새 주문 없음 / `SUBMITTED` 커밋 후 전송 전 종료 → `UNKNOWN` 유지 / 전송 후 응답 전 종료 → `UNKNOWN` → 조회로 확정. 모든 경우 같은 신호로 주문 최대 1건
- [ ] 저널 마지막 줄이 잘린 JSON / 잘린 UTF-8 바이트인 임시 파일 → 새 저널 인스턴스로 재생 시 그 줄만 `.partial`로 보관, 나머지 반영, 다음 seq = 최대 + 1
- [ ] 저널 중간 줄 손상 → 재생 중단, 진입 정지, 알림
- [ ] REST 스냅샷 직후 손절 체결 → 버퍼 재생으로 반영, 안정화 확인 전 진입 없음
- [ ] 개인 스트림 끊김 중 체결 → 재연결 동기화로 복구, 그동안 진입 없음
- [ ] 진입 체결 직후 강제 종료 → 재시작 시 부착 손절과 함께 장부 복구
- [ ] 저장소 장애 중: 진입 차단, 손절 재등록·추적 손절 수정·청산은 저널 기록 후 성공
- [ ] 저장소 장애 중 같은 손절 amend 2회 + cancel 1회 → 복구 후 작업 3건 모두 반영, 최종 상태 = 거래소
- [ ] `requested`만 쓰고 종료 → 재시작 시 거래소 확인 후 반영
- [ ] 저널 기록 실패 → 보호 작업 전송 + 알림
- [ ] 저널 재생을 두 번 해도 결과 동일 (멱등)
- [ ] 조회 지연으로 UNKNOWN 지속 → 예약·정지 유지, 늦은 OPEN 도착 후 정상 추적
- [ ] `trading_lab` 삭제 후 CI 통과, 임시 설정 제거
