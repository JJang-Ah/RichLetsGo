## 범위

### 만들 것

1. **동기화 절차** `Synchronizer` (`oms/`, D47) — 03 4.3절 1~11단계 중 M1 범위
   - 동기화 동안 `ENTRY_PAUSED_SYSTEM(sync)`.
   - 개인 이벤트 스트림 먼저 구독, 이벤트는 버퍼에만 쌓음.
   - REST 스냅샷: 잔고, 포지션, 미체결(조건부 포함), **마지막 저장 체결 시각 − 여유 시간**부터의 체결 내역.
   - 스냅샷 반영(execId 중복 제거, 상태 규칙) → 버퍼 재생 → 보호 확인(전략별 손절 = 보유, 부족분 `PROTECT`, 초과분 취소, 미완료 `CloseIntent` 재개) → **안정화 확인**(포지션 재조회 = 장부; 다르면 스냅샷부터 반복, 횟수 초과 시 정지 유지·알림) → 정지 해제.
   - 마지막 체결 시각이 조회 가능 범위 밖이면 자동 복구하지 않고 정지 유지·알림(범위는 설정값).
   - 시작과 재연결에 같은 절차를 쓴다.
   - **재시작 시 주문 정리 (D60)**: `CREATED`로 남은 주문은 `ABORTED`(보낸 적 없음, 예약 해제, 신호 재평가 없음, 체결 없는 에피소드 종료), `SUBMITTED`로 남은 주문은 `UNKNOWN`으로 바꿔 5.3절 해소에 넘긴다.
   - **귀속 보류 해소 (D61)**: 보류 체결이 기한을 넘기면 거래소 주문 ID로 조회해 결과를 M1-02에 넣는다.
   - **주문 전송기**: 주문을 보내기 직전 `SUBMITTED` 커밋 → 커밋 성공 후에만 `place_order` 호출. 이 순서를 한 함수에 모은다.

2. **로컬 저널** `ProtectiveJournal` (`oms/` 또는 `storage/`, D45·D55)
   - 디렉터리를 pathlib.Path로 주입받는다(03 3.1절). 고정 data/journal 또는 cwd·소스 위치로 경로를 만들지 않는다. 추가 전용 JSON Lines, 한 줄마다 flush + `os.fsync`.
   - 레코드 필드: `operation_id`, `phase`(requested/result), `seq`, `op_type`(create/amend/cancel/close), `target`(orderLinkId, orderId), `request`, `result`, `ts` (03 5.4절 표).
   - **보호·축소 작업만** 저널을 쓴다. 노출 증가 주문(진입)은 저장소 커밋이 실패하면 보내지 않는다.
   - 저장소 장애 모드: `UnitOfWork` 커밋이 실패하면 `ENTRY_PAUSED_SYSTEM(db)` + 보호 작업은 저널 기록 후 전송(정상 전송).
   - **긴급 전송 (D65)**: `requested` 쓰기·flush·fsync 중 하나라도 실패하면 보호 작업은 그래도 보내고, "저널 불확실" 표시(메모리 + 별도 표시 파일)를 남기고 알린다. 표시 파일은 주입받은 저널 디렉터리 안의 `JOURNAL_UNCERTAIN` 파일로 한다(03 3.1절 경로 규칙). 표시 파일 쓰기도 실패하면 메모리 표시만으로 진행한다.
   - **재시작 시 동기화는 표시 파일 유무와 관계없이 항상 D65 대조(거래소의 우리 형식 주문·체결 받아들이기)를 실행한다.** 표시 파일이 사라졌거나 쓰이지 못한 경우에도 중복 보호·청산 주문이 생기지 않게 하기 위해서다. 표시 파일은 알림과 진단용이다.
   - 재생: `seq` 순서로 `(operation_id, phase)` 단위 멱등 반영. `requested`만 있는 작업은 종류별로 거래소에서 결과 확인(create/close: orderLinkId 조회, amend: 현재 trigger 비교, cancel: 상태 확인). 그다음 동기화 절차 실행.
   - 반영 완료 파일은 보관 폴더로 이동.
   - **손상 처리 (D63)**: 프로세스 시작마다 새 구간 파일(`journal-<번호>.jsonl`)에 쓴다. 마지막 줄만 손상(줄바꿈 없음, 잘린 JSON·UTF-8)이면 그 줄을 `.partial`로 옮겨 보관하고 무시. 중간 줄 손상이면 자동 재생 중단, 신규 진입 정지, 알림. 다음 seq = 모든 구간의 정상 레코드 최대 seq + 1.
   - 정상 전송은 `requested` fsync가 끝난 뒤에만 보낸다. 그러나 **잘린 줄이나 레코드 부재를 미전송 증거로 쓰지 않는다**(긴급 전송이 있었을 수 있음). 마지막 줄 손상이 있으면 "저널 불확실"로 표시한다.
   - **저널 불확실 복구 (D65)**: 동기화 절차에서 거래소의 미체결(조건부 포함)·체결·포지션을 읽어, DB에 없는 우리 형식(P/X) 주문·체결은 새로 만들지 않고 받아들인다(orderLinkId의 전략·용도로 귀속). 보호 부족분과 청산 남은 수량은 받아들인 주문을 포함한 거래소 실제 값으로 계산한다. 대조가 끝나기 전에는 신규 진입을 열지 않는다.

## M1-04 보호 복구 연결 (PR #16 검토 반영)

- `ProtectionRecovery`의 복구 ID·보호/축소 각각의 시도 횟수·마지막 시각·체결 후 조회 장벽, 마지막 체결 수신 시각, stop snapshot 시각/revision, 계약 정지 revision을 계좌 UoW와 함께 영속화한다. 재시작 때 카운터를 초기화하지 않는다.
- `confirm_stop_snapshot(symbol, keys, at)`의 `at`은 전체 조회 시작 시각이다. 계좌 이벤트를 버퍼링하고 직렬 반영하며, 조회 도중/이후 체결이 반영되면 그 조회를 재사용하지 말고 다시 조회한다. 부분/실패 응답은 완료로 전달하지 않는다. 실패한 QUERY_STOPS 재시도와 스트림 단절 정지는 M1-06 조정자가 담당한다.
- `recover_system_pause(symbol, exchange_qty, at)`는 동일 동기화 회차의 포지션·손절을 맞추고 버퍼 재생·저널 인수까지 끝낸 뒤 호출한다. 새 조회가 정지 revision보다 뒤여야 한다. 미확정 주문·미반영 체결·귀속 보류·미완료 청산·미인수 주문 outbox가 있으면 거절한다. 성공은 계약 정지만 해제하고 알림 outbox에 기록한다. 수동/HALTED 재개는 기존 위험 엔진 경로를 쓴다.
- 조회에서 사라진 손절은 현재 임시 CANCELLED 처리한다. 실제로는 손절 체결일 수 있으므로 M1-06/M3는 주문 이력과 체결 이력을 대조하고 누락 체결을 반영해야 한다. 미조회만으로 실제 취소였다고 감사 기록을 확정하지 않는다.

## M1-04·M1-05 병합 후 보완 (2026-10-21, Claude Code)

M1-04(PR #16)·M1-05(PR #17)가 병합되면서 생긴 연결 계약을 구현 전에 정리한다. 이 절은 Codex 검토와 사용자 확인 대상이다.

### outbox 작업 실행표

`PortfolioService`의 `uow.portfolio.actions()`를 **계좌 루프 하나가 순서대로** 읽어 실행한다. 이벤트 반영·`tick`·조회 완료와 같은 루프에서 직렬로 돈다(M1-04 연결 계약). 작업 키는 멱등 키다. 실행 책임을 인수한 뒤(정상: `SUBMITTED` 커밋 또는 저널 `requested` fsync, 저장소 장애: 저널) `acknowledge`한다.

| 작업 | 실행 | 저널 대상 | 결과 반영 |
|---|---|---|---|
| `CANCEL_ENTRY` | `cancel_order` | 예(취소는 노출 감소) | 주문 이벤트·조회로. `NOT_FOUND`/`TOO_LATE`는 조회로 확정 |
| `CLOSE`, `REDUCE_UNPROTECTED` | 포트폴리오가 만든 `CREATED` 주문을 `OrderRequest.from_record`로 reduce-only 시장가 IOC 전송(주문 전송기) | 예 | 체결 이벤트. IOC 남은 수량 재시도는 포트폴리오 상태 기계가 새 작업으로 낸다 |
| `PROTECT` | 같은 방식으로 조건부 reduce-only 전송 | 예 | 주문 이벤트 |
| `CANCEL_STOP` | `cancel_order`(부착 손절은 거래소 ID) | 예 | 주문 이벤트·조회 |
| `TRIM_STOP` | 아래 "손절 수량 줄이기" | 예 | 주문 이벤트·조회 |
| `QUERY_STOPS` | 조회 시작 시각 기록 → 미체결(조건부 포함) **전체** 조회 → 각 이벤트 `on_order` → `confirm_stop_snapshot(symbol, keys, 시작 시각)`. 일부 실패·중간 체결 반영 시 완료로 넘기지 않고 다시 조회. 사라진 손절은 주문 이력·체결 내역으로 대조(체결이면 누락 체결 반영) | 아니오(읽기) | 조회 회차 |
| `PAUSE` | 포트폴리오가 이미 계약 정지를 걸었다. 여기서는 알림만 | 아니오 | — |
| `ALERT` | 알림 수신자(M1은 메모리 목록, M3는 텔레그램) | 아니오 | — |

- 전송 실패가 `TIMEOUT`이면 실패로 보지 않고 `UNKNOWN` 해소(03 5.3절)로 넘긴다. 같은 작업을 새 ID로 다시 보내지 않는다.
- 진입 주문은 outbox를 거치지 않는다(위험 게이트 → 주문 전송기). 저널 우회 금지 규칙 그대로.

### 손절 수량 줄이기 (`TRIM_STOP`, 제안 D90)

M1-04의 `TRIM_STOP`은 주문별 **남길 수량**을 담는데, M1-05 `ExchangeGateway`에는 trigger만 바꾸는 `amend_stop`뿐이라 수량을 줄일 방법이 없다. Bybit `amend-order`는 조건부 주문의 `qty`·`triggerPrice` 변경을 지원한다(공식 문서). **부착 Partial 손절의 수량 변경 가능 여부는 문서에 없어서 M3 데모에서 확인한다**(M3-07 C10).

**1. 게이트웨이 확장**: `amend_stop(order_link_id, trigger_price: Price | None = None, qty: Qty | None = None)`. 둘 중 하나 이상은 있어야 한다. 가상 거래소도 같이 지원한다. 이 변경은 M1-05 코드를 고치므로 M1-06 안에서 하되 PR 설명에 별도 항목으로 적는다.

**2. 수량 변환** (PR #18 검토 1번)
- `TRIM_STOP.qty`는 **부호 없는 남길 잔량**(아직 체결되지 않은 수량)이다.
- 게이트웨이 `qty`는 Bybit `amend-order`처럼 **주문 전체 수량**(부호 있음)이다.
- 변환: `새 전체 수량 = 그 주문의 누적 체결 수량 + 남길 잔량`, 부호는 그 손절 주문의 부호. 예: 전체 −2, 누적 체결 1, 남길 잔량 0.5 → 새 전체 수량 −1.5.
- 남길 잔량이 0이면 수량 변경이 아니라 취소(`CANCEL_STOP`과 같은 경로).
- 누적 체결 수량은 변환 직전 로컬 주문 기록 값을 쓰고, 그 값을 저널에 함께 남긴다.

**3. 저널 기록과 재생** (PR #18 검토 1번, 03 5.4절 보완)
- amend 레코드의 `request`에 **바꾸는 필드 목록**(`trigger` / `qty`), 바꾸기 전 값(trigger, 전체 수량, 누적 체결 수량), 요청 값(새 trigger, 새 전체 수량)을 남긴다.
- `requested`만 있는 amend의 재생 판정: 대상 주문을 조회해 상태·trigger·전체 수량·누적 체결을 읽는다.
  - 종결(체결·취소)됐으면 → **대체됨**. 다시 보내지 않는다.
  - 열려 있고 바꾸는 필드가 모두 요청 값이면 → 성공.
  - 바꾸는 필드가 모두 이전 값이면 → 미적용.
  - 그 밖(다른 값, 자동 축소, 다른 amend가 뒤따름) → **대체됨**.
- **재생은 과거 목표를 다시 보내지 않는다.** 판정 결과만 기록하고, 필요한 다음 작업은 포트폴리오가 현재 장부·거래소 상태로 새로 낸다(새 작업 키). 추적 손절의 trigger amend도 같은 규칙.
- Bybit amend 응답은 "접수"일 뿐이므로(공식 문서) 결과는 주문 이벤트·조회로 확인한다.

**4. 수량 변경이 안 되는 손절의 대체 절차** (PR #18 검토 2번)
- 순서: ① 새 작은 `PROTECT` 발행 → ② **전체 손절 조회**로 확인 → ③ 기존 손절 취소 → ④ 다시 전체 조회로 확인. 먼저 취소하는 순서는 쓰지 않는다.
- ② 판정은 아래 순서로 한다. **접수 응답(Accepted)은 보호 확인이 아니다.** 가상 거래소 NEWEST 규칙에서는 접수와 동시에 새 주문이 취소될 수 있고, OLDEST 규칙에서는 기존 손절이 대신 줄어든다.
  1. **이미 목표 상태면 끝**: 그 계약의 모든 전략이 `보호 수량 = 보유량`이면(거래소 자동 축소로 기존 손절이 이미 줄었거나 사라진 경우 포함) ③ 없이 두 주문을 그대로 두고 끝낸다.
  2. **③ 취소 조건** (PR #18 재검토 2번): 취소할 기존 손절의 **남은 수량을 뺀 뒤에도** 그 전략의 보호 수량 ≥ 보유량이고, 다른 전략들도 각각 보호 수량 ≥ 보유량일 때만 취소한다. 예: 보유 1, 기존 0.5 + 신규 0.5 → 기존을 빼면 0.5 < 1이므로 **취소하지 않는다**. 보유 0.5, 기존 1 + 신규 0.5 → 기존을 빼도 0.5 ≥ 0.5이므로 취소한다(교체 중 초과 보호 상태라도 진행 가능).
  3. 둘 다 아니면 아래 분기.
- 분기:
  - 새 주문 `UNKNOWN` → 기존 손절 유지, 5.3절 조회로 해소될 때까지 ③ 금지.
  - 새 주문이 취소·부분 축소됨 → 기존 손절 유지. M1-04 `ClosePolicy`의 보호 재시도 횟수·간격 안에서 다시 시도.
  - 다른 전략 손절이 줄었음 → M1-04 보호 복구 경로로 먼저 메운다. ③은 그 뒤.
  - 거래소가 기존 손절을 대신 줄여 이미 목표 상태 → ③ 없이 끝(조회로 확인).
  - 재시도 한도 초과 → **초과 손절을 그대로 둔다**(reduce-only라 포지션을 새로 열지 않음). 그 계약 신규 진입 정지 + 알림. 미보호 수량이 생긴 경우에만 M1-04 미보호 축소 경로.
- **저널 키** (PR #18 재검토 1번): 복합 작업은 `group_id`(교체 묶음 ID)로 묶고, **거래소에 보내는 요청 하나하나(① 발행, ③ 취소, 재시도마다)에 새 `operation_id`**를 준다. 저널 레코드에 `group_id`·`step`(①/③)·`attempt`를 함께 남긴다. 재생 멱등 키는 지금처럼 `(operation_id, phase)`이고, 묶음의 진행 상태는 같은 `group_id` 레코드들로 다시 만든다(03 5.4절, M3-02 `protective_operations`에 `group_id`·`step`·`attempt` 열 추가).
- 새 orderLinkId는 ① `requested`에 미리 기록하므로, 재시작하면 그 ID로 조회해 ①을 다시 하지 않는다. ③ `requested`만 있고 종료됐으면 기존 손절 상태를 조회해 판정한다(취소됨 → ④, 열려 있음 → ② 판정부터 다시).

### 그 밖의 연결

- **늦은 부착 손절 연결 이벤트**: V0 통합 테스트에 M1-05 `HOLD_ATTACHED` + `release_held()`로 "체결 먼저 → 연결 이벤트 나중(손절 미발동)" 순서를 넣는다. 중복 `PROTECT`가 생기지 않아야 한다(PR #16 P1-1 회귀).
- **커밋 예외 분기** (PR #18 검토 3번): 주문 전송기의 커밋 예외 처리는 주문 종류에 따라 다르다.

  | 경우 | 진입 | 보호·축소(`CLOSE`·`REDUCE_UNPROTECTED`·`PROTECT`·취소·수량 변경) |
  |---|---|---|
  | 커밋 성공 확인 | 전송 | 전송 |
  | 확정된 커밋 실패(COMMIT 전 장애·저장소 장애) | **전송 안 함**, 예약 해제는 재시작 동기화에 맡김 | `ENTRY_PAUSED_SYSTEM(db)` → 저널 `requested` 기록 후 같은 orderLinkId로 전송(D45). 저널도 실패하면 긴급 전송(D65) |
  | 커밋 결과 불명(M3-02) | **전송 안 함**, M3-02 `txn_id` 판정까지 대기 | 저장소 장애와 같은 저널 경로로 전송(보호는 판정을 기다리지 않는다). 판정 뒤 재개 순서는 M3-02 "보호 작업 예외"를 따른다 |

  - 저널 레코드에는 outbox **작업 키**(`action_key`)를 함께 남긴다. 저널 경로로 이미 보낸 작업을 나중에 정상 전송기가 다시 실행하지 않게 하기 위해서다.
  - M1에서는 메모리 UoW 장애 주입으로 "확정된 커밋 실패"만 시험한다: 진입 미전송 1건, 보호 작업 저널 경유 전송 1건. 결과 불명 분기는 M3-02에서 Oracle과 함께 시험한다.
- **펀딩**: `funding`에 정산 시각을 받는 변경(M3-04)은 M1-06 범위가 아니다.
